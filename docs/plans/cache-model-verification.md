# #59 · Cache release model verification across searches

**Decision.** Let Linux fs-verity maintain an authenticated Merkle tree on each qualified managed model file. The executable supplies the expected root from release-verified bytes. A fresh search can authenticate the file in constant time and read it from the same descriptor directly into the adapter’s private buffer. Keep full SHA-256 for unsealed files, unsupported systems, external model paths, status and sync. The owner approved this design on 2026-11-23. There is no daemon, user setting, on-disk receipt or runtime helper program. [Linux fs-verity API and filesystem support](https://docs.kernel.org/filesystems/fsverity.html)

## Expected gain on pax

A short Go microbenchmark read the existing 309,855,520-byte Q8_0 file into a newly allocated `Size+1` buffer with `io.ReadFull`, checked exact size and EOF, and optionally ran `sha256.Sum256` against its release digest. Each sample ran in a fresh process on CPUs 0–3 with `GOMAXPROCS=4`. One initial read primed the file pages. Six timed samples alternated the two arms in pairs. This measured disk-cache read, allocation/copy and userspace hash; it did not load a model or exercise a sealed search.

| Warm operation | All samples (ms) | Median |
| --- | --- | ---: |
| Read plus SHA-256 | 206.6, 208.6, 214.9 | 208.6 ms |
| Read into the same private buffer | 89.9, 96.1, 91.3 | 91.3 ms |

The expected saving is **117.3 ms**. Against the owner’s 561.2 ms Q8_0 rule-3 median that projects **about 444 ms**. The remaining 91 ms copy is included. Cold fs-verity reads can incur kernel block verification; the five production-path samples below decide acceptance. An unprivileged scratch probe on pax’s btrfs successfully enabled version 1, SHA-256, block size 4,096, no salt, and measured a 32-byte digest.

## 1. Bind the fast path to the release

- Extend `embed.File` with `VeritySHA256 [32]byte` (all zero = explicitly no fast path). For all final `Model.Files` of bge-small, Google and Q8_0, supply the measured **fs-verity file digest**, which hashes a descriptor containing the root and length. A plain file SHA-256 or bare Merkle root is a different value. Give download-only `Model.Source` and unqualified test rows zero. Keep the original full SHA-256 mandatory. Store the pins with the corresponding release rows in `internal/embed/bge/model.go`, `internal/embed/gemma2/model.go` and `gguf.go`. Validate row metadata before use. The search looks up the release row in its registry. Local manifests and cache contents never supply pins.
- Check in a developer tool under `tools/model-verity-pins/`. Input is a release model name and a directory of local weights. Run strict `embed.Verify` against the release table first. Compute version-1 SHA-256 fs-verity file digests for **those private bytes**, using 4,096-byte blocks, empty salt, no signature, on every architecture. A portable generator may feed the verified slices to the reference `fsverity digest --hash-alg=sha256 --block-size=4096` via private temporary files (no salt argument). Pin the generation command/version in the tool README. Emit file name, size, full SHA-256 and fs-verity digest. Fail on missing files, failed verification or unsupported tool output. The release binary never invokes the tool. A gated real-file test recomputes **every populated pin** from the pinned bytes and compares it with the row; the release-pin validation job/run must have all three real fixtures and fail if any is missing or skipped. Synthetic always-on tests cover a deliberately wrong pin. Cross-check the generator with Linux MEASURE on known fixtures including a partial block and multiple tree levels.
- The key is the release row’s file name, expected size, SHA-256, fixed verity profile and verity digest, paired with the **current open inode’s** kernel measurement. Its persisted cache is the filesystem’s inode-bound tree. Skip all stat receipts: inode/size/mtime/ctime do not authenticate contents, and a writer can forge a sidecar. Keep `FolderName`, model/index fingerprints and vector cache keys based on the existing model inputs. Metadata added to authenticate identical bytes cannot change embeddings. A changed byte pin requires regenerating the corresponding verity pin even when the path, size and timestamps match.

## 2. Keep the fd, trust boundary and fallback explicit

In `internal/sys` add a small optional native capability with `MeasureVerity(RegularFile) ([32]byte, error)` and `SealTempVerity(Dir, string, io.WriteCloser) ([32]byte, error)`. Implement it on supported Linux builds. Use the already-linked `x/sys/unix`, fixed-width Linux UAPI layouts and the already-open file descriptors. Use a trusted local filesystem type (btrfs, ext4 or f2fs) via `fstatfs`. Unrecognized filesystems, including userspace filesystems offering their own ioctl answers, take the strict path. Other platforms and injected file implementations without this capability also take that path. The fixed block size stays 4,096 on 64 KiB-page arm64. If the kernel/filesystem cannot enable that profile, keep strict verification; never substitute the native page size.

In `internal/embed/embed.go`, factor the existing `readPinned` / `readOne` loop to support **strict**, **strict managed** and **managed search** policies. Keep `Verify(files, dir, m)` as the ordinary strict API. Add `VerifyManaged(files, dir, m, mode)`, with named modes `ManagedStrict` and `ManagedSearch`. Keep the current worker limit, ordered errors, no-follow regular open, own-fd type/size check, bounded exact read and private Artifact. Both verifiers authenticate the row; only managed search can skip hashing. The adapter never reopens a path or receives a mapping of a mutable file.

| Managed file on the descriptor being read | Managed search | Managed strict |
| --- | --- | --- |
| No file pin, no capability, file unsealed (`ENODATA`) or unsupported operation (`ENOTTY`, `EOPNOTSUPP`, `ENOSYS`) | Read and compare full SHA-256 | Read and compare full SHA-256 |
| Kernel returns the release-pinned digest | Read exact bytes from **that fd** into owned memory. Any read/size error rejects the artifact | Also compute and compare the full SHA-256 of those bytes |
| Successful measurement with the wrong digest, algorithm or digest length | `ErrWrongModel` | `ErrWrongModel` |
| Missing entry, unsafe type, unexpected measurement/read error | Use existing absent, wrong-model or I/O handling. Never hand partial bytes to `Registry.Open` | Same |

Request a large enough digest buffer to distinguish a sealed file with another algorithm from a missing measurement. Preserve hard I/O errors. A valid raw hash cannot override a known mismatch on a sealed managed file. An external `model_path` is always read with strict `Verify`, even if it is independently sealed with other parameters. `Find` remains only a name/type/size precheck.

**Invalidation and adversaries.** The kernel prevents in-place writes and writable shared mappings on a sealed inode. Corrupt reads fail. With an unsealed inode, SHA-256 covers the copied bytes, including during a concurrent write. Renaming a different file over the path cannot change an already-open descriptor. The next open validates the replacement, accepting a genuine byte-identical model and rejecting wrong bytes. Hardlink, timestamp restoration, inode reuse and a forged user-writable receipt confer no authority. A cache writer can evict, replace or deny reads. It cannot make alternate model bytes pass a compiled pin while the release executable, kernel and underlying verification implementation are trusted. The cryptographic operation on a hit changes from hashing the whole private slice in userspace to authenticating each page against a release-pinned file digest, then copying those exact bytes. No mmap lifetime or SIGBUS handling is needed.

## 3. Seal only an inode sync created

Implement managed preparation in `internal/semantic/build.go`’s `ensureModel`, under the existing model lock. After a managed **strict** verification succeeds, the Artifact already holds the correct bytes. For an unsealed file with a populated pin on an eligible filesystem, write those bytes into a fresh private temp in the same managed model folder, seal and measure that temp, then atomically `Dir.Replace` it over the managed name and sync the directory. This also migrates valid pre-upgrade caches on their next normal sync. Both new and pre-existing files go through this one path. Do not enable verity on an existing named inode: it might have hardlinks into a user’s offline folder. A status check or search never creates this temp. Source downloads, external `model_path`, caches outside the existing placement checks and a model with no eligible pins never enter this step.

`SealTempVerity` consumes the writer on every exit. While it is still open, open the temp for reading through its folder. Compare the two live fd identities, reject a substitution, flush and close the writer (`Files.Flush` closes it), then enable on the retained **read-only fd**. Require the kernel’s measured value on that same fd to match the expected row before publication. This avoids sealing a different inode after a name swap. An already-sealed file (`EEXIST`) is remeasured. An unsupported enable, including inability to use fixed 4,096-byte blocks on an older kernel, read-only installation, or a busy writer leaves the verified original usable and the temp disposable. Treat those optimization failures quietly. Preserve genuine verification failures, cancellation, unsafe-path errors and I/O errors through their existing categories. Ineligible filesystems should be detected before copying a large file; when only enable will reveal lack of support, probe once per destination filesystem per sync on an owned empty temp before migrating a large unsealed file. Never use that capability result as a content check.

A wrong sealed managed file enters the existing remove-and-reprovision flow. Use the same strict-managed comparison in `badFiles` for final managed files so a disagreeing verity pin is classified consistently by diagnosis and repair; source files still use raw SHA. Unlink/rename whole files. No in-place repair of sealed content. Maintain existing cleanup, lock order and bounded repair attempts. A failed migration or process crash can leave a temp, but only a complete old or new file is ever published. If another party changes the name after publication, the next reader verifies the file it opens independently.

## 4. Wire actual callers and demonstrate the gain

| Caller | Verification and side effects |
| --- | --- |
| `semantic.Source.runModel` | For the managed cache call `VerifyManaged(..., ManagedSearch)`. For `Options.ModelDir != nil` use `Verify`. Continue to open the CPU runtime from the Artifact, embed the query once and preserve lexical fallback, cancellation and preflight behavior. |
| `semantic.modelPresent` / `sync --status` | ManagedStrict for managed files, raw Verify for `model_path`. Always check the full SHA on accepted files. No cache writes, enabling, model load or network. |
| `ensureModel`, repair, download, derive | Strict on sync, including when all vectors are reused. Preserve full transfer/source/pack SHA validation. Only the locked managed sync prepares sealed copies of final verified model files. |
| Rule-3 benchmarks | Keep existing raw `Verify` + open/query controls. Time the production managed search path separately. Both arms consume the same bytes and use the same CPU runtime. |
