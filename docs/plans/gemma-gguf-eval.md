## 4. Measure vector and retrieval quality

1. **Adapter parity and quantization drift answer different questions.** Against an independent reference for each pinned GGUF (e.g. the upstream-qualified llama.cpp build, same file, prepared IDs, pooling and normalization), test all 22 reference inputs at full 768 dimensions and normalized 512-prefix. Require the architecture rule 2 cosine of at least 0.999 on each. Save runtime revision and commands. Also compare same-quant CPU vs CUDA and CUDA singleton vs packed/reordered layouts. Require same-build/device batch invariance by bits. Keep the Google pack's existing sentence-transformers references for A and B. Missing independent references leave rule 2 open for that quant.
2. **Per-passage drift.** Save every finite, unit-length 768-vector from both fixture sizes and both devices. Join on section, path, passage ordinal, bounds and digest, verify complete one-to-one coverage, compute cosine in float64, and keep the per-passage values. Report count, minimum, fifth percentile, median and worst passage ID. Compare B:A, C:B and D:B within each device and report CPU:CUDA within each arm. Report byte equality separately. A Q6–Google cosine below 0.999 measures loss from quantization. It does not by itself fail Q6's same-file adapter check.
3. **Product retrieval.** For each model, use `internal/semantic/calibrate` with `-model NAME -model-path DIR -stage calibration` and then `-stage check` on `internal/semantic/calibrate/testdata/retrieval`. Use the existing cutoff procedure on the 30 calibration negatives. Freeze its result before looking at 30 held-out negatives and 47 answerables. Keep the standalone and combined gates, strict-loss/regression IDs, and private replay checks. Reproduce the Google arm's historical 42/47 first-page and 30/30 abstention, or explain the difference. 4. **Top-ten overlap.** For each identical question compare C and D separately to B, and B to A. Report two views. ## 5. What v0.6.0 supplies for #41

`(*Encoder).UseAutoAccelerator(preferred ...string) AcceleratorChoice` tries linked backends in order (default CUDA then Vulkan), keeps an existing attachment, and returns the chosen backend/selector and declined attempts. It selects CPU when no attempt succeeds. pbrain still needs its own ordering by memory kind, basis and free bytes and its explicit-selector error behavior. A user naming one GPU must see an attachment failure. Search keeps the CPU path. [Upstream auto selection](https://github.com/pkieltyka/goinfer/blob/v0.6.0/embeddinggemma2/auto.go)

The optional `github.com/pkieltyka/goinfer/backend/vulkan` module registers direct Vulkan on Linux/amd64. It uses pure Go bindings to the Vulkan loader (`libvulkan.so.1`) and the AMD driver. A pbrain `linux && amd64 && vulkan` blank-import file could link it beside the existing CUDA import. The root tag has no corresponding nested Vulkan release tag. Its tag-aligned pseudo-version is `v0.0.0-20261122153515-4192e6d77e3b`; the tag-aligned CUDA module is `v0.5.1-0.20261122153515-4192e6d77e3b`. Use these pseudo-versions only in a disposable linkage probe. A release dependency must resolve through a module-specific tag on upstream main. goinfer needs to publish matching nested tags (e.g. `backend/cuda/v0.6.0` and `backend/vulkan/v0.6.0`) at each root release, with the same peeled commit and proxy-verifiable content. If testing linkage for #41, build CPU, CUDA, Vulkan and dual-tag registration probes/CLI with identical flags and report sizes/deltas. Assert both backend names in the dual binary without attaching either. Actual Vulkan vector parity, device memory and speed need a separately available AMD machine. [Vulkan module at the tag](https://github.com/pkieltyka/goinfer/tree/v0.6.0/backend/vulkan)
