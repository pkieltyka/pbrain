# Memory and the learning loop (Hermes Agent)

## Bottom line

Hermes Agent (Nous Research, MIT; read at `main` @ `d3ecbeeb`, 2026-11-26, v0.23.4) keeps memory in three tiers:

1. Two tiny agent-curated Markdown files, `MEMORY.md` (2,200 chars, about the environment) and `USER.md` (1,375 chars, about the user). They are injected into the system prompt as a **frozen snapshot at session start**.
2. Every transcript is kept in a per-profile SQLite DB, which the agent searches on demand with `session_search` (FTS5, **no LLM since May 2026**).
3. Optionally, **one** external provider (Honcho, Mnemosyne, Mem0, Hindsight, …) plugs in through a `MemoryProvider` ABC with before-turn, after-turn, boundary and mirror hooks.

The "learns by doing" loop is a **background review fork**. After a turn is delivered, a copy of the agent replays the conversation on the warm prompt cache with a fixed review prompt and a whitelist limited to memory and skill tools, then writes memory entries and skill patches. It fires every 10 user turns (memory) or every 10 tool iterations (skills), or on demand via `/refine`. The prompts route task knowledge, including the user's corrections for a kind of task, into **skills**. Memory is kept for cross-task facts. They also forbid inferring user traits that aren't grounded in the conversation. An optional `write_approval` gate stages writes for human review.

## Key findings

- **Bounded, char-limited, no auto-compaction.** An overflowing write errors with the current entries, and the model must remove or patch entries and add the new one in one atomic batch. Entries are separated by `§`. Actions are `add`/`patch`/`remove`. `replace` was removed because models wiped multi-fact entries with it. There is no read action. — [builtin-memory-stores.md](./builtin-memory-stores.md), [memory docs](https://github.com/NousResearch/hermes-agent/blob/d3ecbeeb09523d1c76264cae0e22d84fde59102a/website/docs/user-guide/features/memory.md)
- **The frozen snapshot trades freshness for prompt-cache hits.** Mid-session writes reach disk but only show up in the *next* session. Hermes' own docs admit the loop "almost never gets to fire" in long-lived gateway chats, and tell users to `/new` at natural boundaries. — same
- **Nudge = a counter-triggered fork, not an in-chat reminder.** `memory.nudge_interval: 10` counts user turns. `skills.creation_nudge_interval: 10` counts tool-loop iterations. The fork runs after delivery and is skipped for cron, subagents and one-shot runs. It is capped at 16 iterations and an input budget of 75% of the window (max 600k). It can be routed to a cheaper model, which gets a digest of the conversation instead of the full transcript, and it can be disabled. — [learning-loop-background-review.md](./learning-loop-background-review.md), [background_review.py](https://github.com/NousResearch/hermes-agent/blob/d3ecbeeb09523d1c76264cae0e22d84fde59102a/agent/background_review.py)
- **User modelling in core is prompt discipline, not inference.** The review must "Save only facts GROUNDED in this conversation ... Never infer the user's traits ... never turn a one-off request into a standing preference" unless it is marked general. Deeper modelling is outsourced to Honcho (peer representations, dialectic LLM reasoning on a cadence, "conclusions"). — learning-loop doc, [memory-providers-and-hooks.md](./memory-providers-and-hooks.md)
- **Interface to skill creation.** The same fork handles both. Preference order: patch a loaded skill → patch an umbrella → add a support file → create a class-level skill. It enforces read-before-write, never deletes, and leaves consolidation to the separate idle-triggered **curator**. One rule: "A user-preference lesson lives in exactly ONE place". — learning-loop doc
- **Write safety.** All memory content is threat-scanned for injection and exfiltration patterns. `write_approval` stages writes (`/memory pending|approve|reject`, `/skills diff`). Staged destructive edits are pinned to the exact entry. Background destructive edits always stage. The gate does not cover direct file edits in foreground turns. — builtin doc
- **Session search is raw, bounded, and not private within a profile.** It has four shapes (discover, scroll, read, browse), demotes cron sessions to avoid "recall blindness", and caps read output at 2,000 chars per message. "anyone allowed to talk to it can ask the agent to find and read anyone else's conversations." — [session-search-and-recall.md](./session-search-and-recall.md)
- **Provider plug-in contract.** Required: `is_available` (no network), `initialize`, tools, and config. Optional: `prefetch` (before turn; injected into the *user message* inside a `<memory-context>` fence with an "authoritative reference data" note, then scrubbed from output), `queue_prefetch`, `sync_turn` (must not block), `on_session_end` and `on_session_switch` (run serialised), `on_pre_compress` (with an opt-in fail-closed checkpoint, v2), `on_memory_write` (mirrors built-in writes), `on_delegation`, and profile hooks. The manager enforces one external provider, scrubs secrets on egress, applies timeouts and a circuit breaker, isolates profiles, and keeps providers out of forks. — providers doc, [memory_provider.py](https://github.com/NousResearch/hermes-agent/blob/d3ecbeeb09523d1c76264cae0e22d84fde59102a/agent/memory_provider.py)
- **Mnemosyne** plugs in purely as a provider (42 tools, no generic hooks). It is local SQLite with vector + FTS5, captures turns including tool calls, injects recall through a conservative lexical gate, consolidates with `mnemosyne_sleep`, and advises disabling built-in memory. **Honcho** is cloud or self-hosted, declares `on_session_end`, and sends turns off-device. — providers doc
- **Generic hooks** for non-provider plugins: `pre_llm_call` (inject context or block a turn), `post_llm_call` (gets `review_signals` so plugins can follow the learning cadence), `on_session_finalize`/`reset`, `post_compaction`, `post_curator_run`, `on_skill_lifecycle`, and cache-safe `register_system_prompt_section` (4k each, 8k total). Gotcha: the plugin `on_session_end` fires after every turn. — providers doc
- **Docs and marketing lag the code.** The README still claims "FTS5 session search with LLM summarization", which was removed in #27590 (2026-05-18). April 2026 write-ups describe `replace` and in-session "system-level prompt" nudges. — session-search doc

## Open questions / gaps

- **No measurement of loop quality.** The docs claim the cheaper-model review is "~3–5×" cheaper with "identical" memory capture, but I found no published eval data. `evals/session_search_schema/` exists, and I did not read its results.
- **Honcho injection point.** The Honcho docs say "system prompt". The provider contract implies the user message. I did not read `hermes-plugin-honcho` source to settle it.
- **Earlier nudge mechanism.** I could not confirm from git history whether pre-May-2026 nudges were injected into the live conversation. The review code was extracted from `run_agent.py` on 2026-05-17, and the mechanism is older than that.
- **`flush` agent context / `flush_memories`.** These appear in docstrings and tests (likely a legacy pre-compression memory-flush auxiliary call). I could not find a current config key or call path.
- I did not read the Hindsight, Mem0, Supermemory or OpenViking plugin sources. Only their catalog and docs summaries.
