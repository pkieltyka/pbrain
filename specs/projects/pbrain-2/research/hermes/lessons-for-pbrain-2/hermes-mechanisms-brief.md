# Hermes mechanisms that matter to pbrain-2 (light pass)

2026-11-26 · inputs for the pbrain-2 functional spec

This is a short, sourced description of the parts of Hermes Agent that pbrain-2 might borrow. Other subtopics in this research cover the skill mechanism, the memory loop and user reports in depth. Here I only record what the mapping in [borrow-and-refuse.md](./borrow-and-refuse.md) depends on.

**Which Hermes.** Nous Research's Hermes Agent, MIT licence, repository `NousResearch/hermes-agent`. GitHub API at review time: default branch `main`, latest stable release `v0.23.4` (2026-11-24), with daily canary tags. I read source at main commit `4b38ec1b664feb0f08da7e7d0971e962ced0d33b`. The docs pages carry no version or date beyond a "2026" footer, so the code is the authority where they differ. This is the same harness Mnemosyne's `integrations/hermes` adapter targets (the Mnemosyne comparison describes its memory-provider registration).

**Label key.** **Code** = I read the pinned source. **Docs** = the official docs site says so; not checked against code. **Issue** = a GitHub issue report (anecdote from one install unless stated).

## 1. The learning loop is a background review fork with counters

- **Code.** Two counters decide when the agent reviews itself: "user turns since the last memory review (`memory.nudge_interval`) and tool-calling iterations since the last skill review (`skills.creation_nudge_interval`)". Both default to 10. [review_signals.py](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/agent/review_signals.py) · [agent_init.py L1177-L1222](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/agent/agent_init.py#L1177-L1222) · [config_defaults.py memory block](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/hermes_cli/config_defaults.py#L1265-L1276)
- **Code.** When due, Hermes "may spawn a daemon thread that replays the conversation snapshot in a forked `AIAgent` and asks 'should any skill/memory be saved or updated?'. Writes go straight to the memory + skill stores; the main conversation and prompt cache are never touched." The fork reuses the parent's model, credentials and cached system prompt. Cron sessions and delegated children are excluded. [background_review.py L1-L6](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/agent/background_review.py#L1-L6) · [review_signals.py](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/agent/review_signals.py)
- **Code.** The fork runs under a dispatch-side tool whitelist: the skills toolset, plus the memory toolset only when the memory counter fired, plus `read_file`/`search_files`. "Write tools (write_file/patch/terminal) stay denied — autonomous maintenance must go through skill_manage's validation." [background_review.py L1212-L1252](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/agent/background_review.py#L1212-L1252)
- **Code.** Writes are tagged with an origin, `foreground` or `background_review`, plus an attended/unattended flag. The curator only curates skills the background review created ("skills a user asked for belong to the user"), and an unattended review cannot delete memory. [skill_provenance.py](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/tools/skill_provenance.py)

## 2. What the review prompts say

All three prompts live in [background_review.py L441-L660](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/agent/background_review.py#L441-L660). The parts that carry over:

- **Code. Grounding rule (memory).** "Save only facts GROUNDED in this conversation — a user message or tool result you can point to. Never infer the user's traits, skill level, role, mood or preferences from topic, tone or tools used, and never turn a one-off request into a standing preference … If unsure, leave it out — a wrong fact misleads every future session."
- **Code. One fact, one store.** "One fact goes to ONE store, never both". A code comment says this was added after "the reviewer wrote profile data into MEMORY.md and the same lesson into both stores until both hit their size limits (#30220)".
- **Code. Skill shape.** A skill is "the instructions for doing a class of task the most efficient and correct way". Rules: procedure first; "A pitfall is a generalizable rule + one clause of WHY"; "No PR/issue numbers, dates, ticket IDs, or quoted user text as content"; "The same lesson learned twice is ONE rule"; "Not a duplicate of what the environment already teaches: repo AGENTS.md files, tool schema descriptions"; "Fix the skill in place when it is wrong … do not append 'UPDATE: actually...'".
- **Code. Do-not-capture list.** Environment-dependent failures, "Negative claims about tools or features … These harden into refusals the agent cites against itself for months", transient errors, one-off task narratives, and "Unresolved failures … do NOT write those attempts up as a 'reliable workflow'".
- **Code. Update before create.** Preference order: patch a skill loaded this session, then an existing umbrella, then add a support file, and only then create a new class-level skill. The name must not be a PR number or a "fix-X / debug-Y" artifact.
- **Code. Read-before-write is enforced.** "before you patch or edit an existing skill's SKILL.md, call skill_view(name) for that skill during this review … Content quoted earlier in the conversation transcript does NOT count".
- **Code. Activity bias.** The skill prompt opens: "Be ACTIVE — most sessions produce at least one skill update, even if small. A pass that does nothing is a missed learning opportunity, not a neutral outcome." Issue #30220 argues this biases the reviewer toward false positives (below).

## 3. Memory files and recall

- **Docs + Code.** `MEMORY.md` (agent notes: "environment facts, conventions, and things learned") and `USER.md` (user profile) live in `~/.hermes/memories/`. They are user-scoped and outside any project repository. Caps are `memory_char_limit: 2200` ("~800 tokens") and `user_char_limit: 1375` ("~500 tokens"). [Memory docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory) · [config_defaults.py](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/hermes_cli/config_defaults.py#L1265-L1276) · [Which file does what](https://hermes-agent.nousresearch.com/docs/user-guide/which-file-does-what)
- **Docs.** "The system prompt injection is captured once at session start and never changes mid-session." Writes reach disk at once and show up in the next session. The memory tool has `add`, `patch` and `remove`, but no `read`.
- **Docs.** Memory entries "are scanned for injection and exfiltration patterns before acceptance"; prompt injection, credential exfiltration, SSH backdoors and invisible Unicode are blocked.
- **Docs.** `session_search` runs SQLite FTS5 over every stored session (`~/.hermes/state.db`) and returns the actual messages. External providers (Honcho, Mem0, Hindsight, etc.) run "alongside built-in memory and never replace it".
- **Docs.** Project-scoped context is a separate, human-written file: `AGENTS.md` or `.hermes.md`, with "first match wins". The agent does not write it through the memory tool.

## 4. Skills storage, approval and curation

- **Docs + Code.** Agent-created skills go to `~/.hermes/skills/` (or `skills.create_dir`). `skill_manage` supports `create`, `patch` (preferred), `delete`, `write_file` and `remove_file`. Skills load by progressive disclosure: `skills_list()` gives about 3k tokens of name, description and category; `skill_view(name)` gives the full file; `skill_view(name, path)` gives a reference file. [Skills docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills?format=md)
- **Code.** Project skills in `<root>/.hermes/skills/` or `<root>/.agents/skills/` of a Git checkout load as the highest-precedence tier "ONLY if the root is in trusted_project_dirs". The curator never modifies project skills. [config_defaults.py L1397-L1412](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/hermes_cli/config_defaults.py#L1397-L1412)
- **Code.** The write-approval gate is off by default for both memory and skills. When on, it "never commits directly: it prompts inline (memory, interactive CLI only) or **stages** the write under `<HERMES_HOME>/pending/{memory,skills}/<id>.json`". It is enforced only inside the `memory` and `skill_manage` tools; "the generic file tools (`write_file`/`patch`) do not consult it (#60440 tracks closing that gap)". [write_approval.py L1-L13](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/tools/write_approval.py#L1-L13)
- **Code.** `skills.guard_agent_created` (default `False`) is a heuristic content scanner, not an approval gate. The docs say the `skill_manage` linter warns but "never block[s] a write". [config_defaults.py L1420-L1425](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/hermes_cli/config_defaults.py#L1420-L1425)
- **Code.** The audit ledger is on by default: "every skill mutation appends to ~/.hermes/skills/.curator_ledger.jsonl with before/after hashes … powers `hermes curator ledger` / `rollback <entry-id>`. Never a gate — failures can't block." [config_defaults.py L1430-L1440](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/hermes_cli/config_defaults.py#L1430-L1440)
- **Docs (repo).** The curator runs on inactivity (default every 7 days, after 2 idle hours), with no cron daemon. Its deterministic pass marks skills unused for 14 days `stale` and moves skills unused for 30 days to `.archive/`. It "never auto-deletes". An LLM consolidation pass that merges skills into umbrellas is "OFF by default because it costs aux-model tokens on every run and makes broad structural changes". Pinned skills cannot be deleted by the agent. Locked skills cannot be changed by it. [curator.md](https://github.com/NousResearch/hermes-agent/blob/4b38ec1b664feb0f08da7e7d0971e962ced0d33b/website/docs/user-guide/features/curator.md) · [#7816](https://github.com/NousResearch/hermes-agent/issues/7816) (closed 2026-04-30)

## 5. Failure reports that shape the lessons

- **Issue #105921 (an unattended fork deleted memory).** A skill-nudge review held the memory toolset. Its prompt was the skill prompt. The memory tool's near-limit message told it to "Consolidate now", so it removed five `MEMORY.md` entries, four of them "**permission gates** the user had accumulated over months". "The user was not told. The deletions were only found the next day by diffing `MEMORY.md` against the last automatic git commit." The current code closes this by gating the memory tool on the trigger that fired (the whitelist above). [Issue #105921](https://github.com/NousResearch/hermes-agent/issues/105921)
- **Issue #32858 (open, 2026-05-26: instructions recorded as user traits).** The review prompt is sent as a `user`-role message, so the fork wrote the prompt's own rules into `USER.md` as the user's preferences, for example "ydawei expects the AI to be active in updating the skill library". Those entries then went to Honcho. [Issue #32858](https://github.com/NousResearch/hermes-agent/issues/32858)
- **Issue #30220 (misrouting and duplication).** The reviewer put facts in the wrong store and duplicated them across stores. The issue also argues that "Be ACTIVE" "biases the model toward saving *something* even when nothing is worth saving". The routing fix is in the current prompts. The activity bias is still there. [Issue #30220](https://github.com/NousResearch/hermes-agent/issues/30220)
- **Gate bypass (#60440, cited in code).** Approval is per tool, so a generic file write bypasses it.
