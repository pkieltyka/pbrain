# Failure modes reported in the Hermes Agent tracker and write-ups

Scope: what users report going wrong with Hermes Agent's (NousResearch/hermes-agent) self-written skills and agent-curated memory. Mechanisms are described only as far as needed to read a report; the skill and memory subtopics own the mechanics. All issue data was read with `gh api` on 2026-11-26 (main at `4b38ec1`, latest release v0.23.4, 2026-11-24).

**Evidence labels.** *Measured*: the reporter gives counts from logs, ledgers or files and says how. *Reproduced*: steps given and the cause is traced to code. *Anecdote*: one user's experience, no counts.

Note on the tracker: most of the substantive reports come from users with author association `NONE` or `CONTRIBUTOR`; several triage comments are AI-generated (they say so). I found no maintainer post that disputes the failure reports below; the fixes that landed are mostly prompt changes or opt-in gates.

## 1. Skill bloat and near-duplicates

- **Near-duplicates pile up; curator does not dedupe.** [#67582](https://github.com/NousResearch/hermes-agent/issues/67582) (open, 2026-07-19): "152 skills on disk, 22 zero-use near-duplicates — e.g. ai-voice-cloning / ai-dubbing-voice-cloning vs the in-use cosyvoice2-voice-cloning ... The user had to manually rm -rf 17 of them." The agent "only guards against the same name (overwrite), but a skill with a slightly different name and ~90% identical content slips right through." Consolidation is opt-in (`curator.consolidate`, still `False` in `hermes_cli/config_defaults.py` on main). *Measured (file counts).*
- **Production audit, 4-agent deployment, 182 skills** (comment by gfpyc on [#96704](https://github.com/NousResearch/hermes-agent/issues/96704), 2026-08-29, Hermes v0.20.x): three same-topic clusters created within hours, e.g. `server-platform-verification` → `server-hardware-acceptance` → `server-hardware-verification` "3 skills in 8 hours, each ~100 lines / 6–7 KB, zero references"; `web-search-security` vs `web-search-safety` same day. Counter-evidence given honestly: "outside these clusters, pairwise overlap across all other suspicious pairs was 0–3% ... Duplication is *not* pervasive — but when it happens it is textbook." Cleanup: "182 skills → 13 description fixes, 1 merge (three-into-one), 13 re-categorized, 4 deletion candidates". *Measured (`.usage.json` ledgers + skill dirs).*
- **Earlier deployment, 70 agent-created skills over ~5 months**: "several have `use_count = 0` since creation weeks ago" (gfpyc, [#96704](https://github.com/NousResearch/hermes-agent/issues/96704), 2026-08-27). *Measured.*
- **Skills that duplicate the knowledge base.** Same audit: "the review still produced large skill copies of it [the docs]... An obsolete `cmp-170hx-unlock` carried 13 key data points ... fully covered by two separate doc locations." The reviewer "has no awareness of the project knowledge base as a knowledge carrier". *Measured.* (Directly relevant to pbrain-2: skills vs docs boundary.)
- **Memory duplicating skills.** [#20595](https://github.com/NousResearch/hermes-agent/issues/20595) (closed, 2026-05-06): a MEMORY.md at "99% (2,187/2,200 chars)" held a 1,099-char spec dump and three entries that duplicated existing skills or AGENTS.md; pruning took it "2,187 → 1,289 chars". Hygiene warnings were "advisory-only ... models ignore the warning". The reporter's diagnosis: "Completion bias is a cognitive failure mode, not a prompt-attention failure." *Measured.*
- **Bundled-skill bloat (not agent-written, but same token cost).** [#19986](https://github.com/NousResearch/hermes-agent/issues/19986) (open, 12 comments) asks to stop seeding non-core bundled skills. Hacker News user andy_xor_andrew: "there were lots of useless garbage skills enabled, over 10k of context used just to list them all" ([HN thread](https://hn.svelte.dev/item/48586005), ~mid-2026). A Phemex news summary (2026-04-30) claimed that before the Curator "a bloated skill list consum[ed] 4,400 tokens per conversation" ([Phemex](https://phemex.com/news/article/hermes-agent-introduces-skill-retirement-mechanism-with-curator-feature-77622)); secondary, no source given. The official Curator doc states the motive without numbers: "Without maintenance, you end up with dozens of narrow near-duplicates that pollute the catalog and waste tokens" ([Curator docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/curator)).

**Root cause users point at: the review prompt is biased toward writing.** [#30220](https://github.com/NousResearch/hermes-agent/issues/30220) (closed "completed" 2026-09-19) quotes `_COMBINED_REVIEW_PROMPT`: "Be ACTIVE — most sessions produce at least one skill update. A pass that does nothing is a missed learning opportunity, not a neutral outcome." I checked `agent/background_review.py` on main (2026-11-26): the phrase is still present (lines ~533 and ~608), alongside "'Nothing to save.' is a real option but should NOT be the default." So the bias the reports blame has not been removed, as far as the current source shows.

## 2. Wrong skills: learned helplessness, mis-named, premature, mis-evolved

- **Learned helplessness from transient failures.** [#6051](https://github.com/NousResearch/hermes-agent/issues/6051) (closed 2026-05-10, fixed by a prompt change in PR #23004): after a WSL2 migration, Playwright was missing; Hermes auto-created `browser-tool-launch-issue` and wrote "browser tools do not work" into other skills. After Playwright was installed "the agent continued to avoid browser tools entirely ... After manually deleting the negative skill ... the agent immediately resumed normal browser tool usage." *Reproduced.*
- **Mis-labelled skill.** [#4538](https://github.com/NousResearch/hermes-agent/issues/4538) (v0.6.0, nemotron-3-super): a one-off tokenomics question produced a skill named `company-research-summary`. *Anecdote with steps.*
- **Premature crystallisation.** gfpyc ([#96704](https://github.com/NousResearch/hermes-agent/issues/96704)): "Within roughly ten seconds of that output — before the user had responded — the same text appeared nearly verbatim in a skill file, timestamped 'tested today', written by the background review fork" — a proposal the user then rejected. *Measured (timestamps).*
- **Silent mutation of a working skill (the most severe report).** Same comment: a user-built `chrome-devtools-mcp` skill ("32+21 patches, used dozens of times") was rewritten by a night-time review fork with the wrong rule "you must close ALL Chrome windows before starting the debug instance", "with **no ledger entry** (the review writes files directly, bypassing `skill_manage` bookkeeping)". It "nearly caused the agent to kill the user's everyday Chrome (losing all open tabs)". The reporter asks that "review writes to existing, user-validated skills must require human approval". *Measured (mtime vs ledger).* A later commenter (glromero, 2026-11-06) ties this to the misevolution paper (see [measurements](./measurements-and-benchmarks.md)).
- **Self-validation.** [#25833](https://github.com/NousResearch/hermes-agent/issues/25833) (open, 10 comments): "the agent is simultaneously the **author**, **executor**, and **quality inspector** of its own skills"; fixes so far are "prompt-level or post-hoc mitigations, not mechanism-level guarantees"; no reproducibility check, no cross-session consistency check. Echoed by a DEV write-up: "compounding confidence, not compounding quality" ([pvishalkeerthan, DEV, 2026-05-18](https://dev.to/pvishalkeerthan/the-self-trust-problem-in-hermes-agents-skill-architecture-18bi)). Community quote "It always thinks it did a good job. ALWAYS." is attributed to a 107-upvote Reddit post with no link ([weihaoqu wiki](https://weihaoqu.github.io/learnAIDoc/wiki/hermes-agent-self-improving-ai/); [Pickaxe](https://pickaxe.co/post/self-improving-ai-agents)) — *unverified anecdote*.
- **Human gate requests.** [#41444](https://github.com/NousResearch/hermes-agent/issues/41444) (open) asks for a "human confirmation gate and provenance tiers for auto-created skills", arguing that a second LLM "carries the same domain-model assumptions as the primary". [#26298](https://github.com/NousResearch/hermes-agent/issues/26298) (confirm before create/overwrite) was closed `not_planned` on 2026-06-12; a later issue says it was "labeled implemented-on-main", which matches the `skills.write_approval` / `memory.write_approval` gates that exist in `config_defaults.py` — both default `False`. The forge/self-evolution repo, by contrast, routes every change through PR review (see measurements doc).

## 3. Stale skills and lifecycle breakage

- **No staleness metadata.** [#25833](https://github.com/NousResearch/hermes-agent/issues/25833)/the DEV write-up: no `last_verified_at`, model-version or expiry; a skill built on a deprecated endpoint keeps being applied.
- **Rot after supersession.** gfpyc: an obsolete skill still referenced "a **retired server name**, a **deprecated working path**, and self-references to 'see the newer skill'"; `skill_usage` "transitions on silence, which cannot distinguish 'a skill nobody needed' from 'a skill nobody could trigger'".
- **Curator consolidation breaks dependants.** [#26326](https://github.com/NousResearch/hermes-agent/issues/26326) (open): the curator deleted `school-teen-radar` into an umbrella skill but "Zero cron jobs were scanned"; the job "silently fails every tick". See also [#18671](https://github.com/NousResearch/hermes-agent/issues/18671), [#23398](https://github.com/NousResearch/hermes-agent/issues/23398). [#79295](https://github.com/NousResearch/hermes-agent/issues/79295): "built-in skills seeded before first curator run are all marked stale".
- **Compaction drops loaded skills.** [#86421](https://github.com/NousResearch/hermes-agent/issues/86421) (open): after compression only a `[SKILL_PRUNED ...]` tombstone remains; "nothing enforces the reload".

## 4. Skills written but not used

- [#66180](https://github.com/NousResearch/hermes-agent/issues/66180) (open, 2026-07-17, Desktop user): two skills captured a recurring `.env` corruption accurately; on the next related task "The agent did not load either skill", the same corruption happened ("the **4th or 5th time**"), and the review fork then added *more* warnings to the unused skills. "The mechanism writes more documentation about errors it could never prevent." Title calls the loop "a net negative for budget-model users". A second user: "Very confident and helpful suggestions to make these things into skills ... but then they don't get actioned because they have to be called." *Anecdote, detailed.*
- [#4589](https://github.com/NousResearch/hermes-agent/issues/4589) (open): skills load only if the model obeys one system-prompt line; "works somewhat with strong models (Claude, GPT-4o) but almost never with smaller models (Qwen, Llama, Mistral etc.)". *Anecdote.*
- **Trigger window.** gfpyc: the chooser surfaces "roughly the first 57 chars" of the description; a mainstay 199-char description truncated at "...known issues, and bre" — "zero trigger words in the effective window". 13 skills were over 57 chars. Its 60 uses came "because agents know it by name ... not because the matcher found it". *Measured.*

## 5. Memory pollution

- **Irrelevant memory hijacks intent.** [#22563](https://github.com/NousResearch/hermes-agent/issues/22563) (v0.13.0, MiniMax-M2.7): a new session asking to "test model access" saw all 9 project memories injected and went off testing CocoIndex tools; the memory also recorded a feature as "a bug" — "the memory system's tendency to save incorrect information". *Reproduced.*
- **No timestamps, no cleanup, cap deadlock.** [#66654](https://github.com/NousResearch/hermes-agent/issues/66654) (open): wrong entries persist; at the hard cap (2,200 / 1,375 chars) "garbage fills up, useful information can't get in" (translated); entries have no created/modified/read metadata. *Code-level analysis.*
- **"A second, worse session history."** [#135039](https://github.com/NousResearch/hermes-agent/issues/135039) (open, 2026-10-08): "memory accretes into a second, worse session history — stale facts, imperative phrasing that hijacks later sessions, duplicated procedures — and the curation pass becomes a manual archaeology exercise." Asks for write-time budget, declarative-only shape check, "belongs in skills" routing, and an audit log.
- **Background writer bypasses user rules.** [#30220](https://github.com/NousResearch/hermes-agent/issues/30220) comment (zhangyi101, 2026-06-17, translated): the user had built "filter → sort → condense → user-confirm → write" rules for their agent and found "the background self-starting agent is completely outside my control"; USER.md had silently overflowed. They later built a DB-first memory layer with provenance tags ([gist](https://gist.github.com/zhangyi101/6426b888a2186f5ab84814bdef291291)). Same commenter found `user_char_limit` limits writes through the tool only: a 3,461-char USER.md was injected whole against a 2,500 limit.
- **Self-contradicting and budget-filling review writes** (gfpyc): "a review-written memory entry contained a self-contradictory date"; review writes "drove memory usage to 99% of the char budget". "Memory is injected into every turn, so the blast radius of a bad memory write is larger than a bad skill write."
- **Machine text saved as user facts.** [#141912](https://github.com/NousResearch/hermes-agent/issues/141912) (open, 2026-10-20): cron boilerplate and delegation notices arrive as USER-role text, so memory providers store them — "chronic junk-memory source".
- **Stale-snapshot overwrites.** [#9055](https://github.com/NousResearch/hermes-agent/issues/9055) (open since 2026-04-13): the review fork reasons over a `messages_snapshot` but writes to the live store, so it can overwrite newer entries from other sessions or cron. A partial fix (PR #39806) is still open per a July triage comment. gfpyc reports the live version: main agent and review edited the same skill minutes apart; "The resulting skill was a blend of two writers' intent".

## 6. Privacy and secret leakage

- [#20785](https://github.com/NousResearch/hermes-agent/issues/20785) (closed 2026-05-07): "Agents running Hermes consistently leak credential values in chat output and reasoning/thinking blocks"; root cause 1: "Credentials stored in agent memory get quoted verbatim"; "Users are trying to solve this with custom skills and system prompt hardening -- none of it works". *Anecdote, but framed as recurring.*
- [#13686](https://github.com/NousResearch/hermes-agent/issues/13686) (closed): the inverse — the `skills_guard` regex scanner hard-blocked agent-created skills that merely mentioned `$HOME/.hermes/.env` or curl URLs; "ask" verdict was a silent block. Today `skills.guard_agent_created` defaults to `False` (config_defaults.py on main), i.e. agent-written skills are not scanned by default.
- [PYSEC-2026-2511](https://osv.dev/vulnerability/PYSEC-2026-2511) (published 2026-07-13): before 0.16.0 Hermes created `response_store.db` and webhook files "with world-readable permissions (mode 0o644), exposing conversation history and HMAC secrets to local users". CVE-2026-10223 (memory-content scanning weakness up to 2026.4.30, allowing remote injection) was reported by search results from NVD/GitLab advisories; I could not load the NVD page, so treat its details as unverified.
- Memory poisoning write-ups I read are hypothetical, not incidents on Hermes ([DEV, vaishnavi_gudur](https://dev.to/vaishnavi_gudur/securing-hermes-agent-against-memory-poisoning-51b1): "Consider a scenario..."; tests ran against the author's own library).
- Shared-vs-personal: [#141912](https://github.com/NousResearch/hermes-agent/issues/141912), [#34352](https://github.com/NousResearch/hermes-agent/issues/34352) ("Solving the Multi-Tenant Hermes Problem") and [#147340](https://github.com/NousResearch/hermes-agent/issues/147340) ("skill lifecycle model for multi-profile installs — scope, ownership, name collisions") show the skill/memory stores were designed for one user; I did not research these further.
