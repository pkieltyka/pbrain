# pbrain-2: proposal

The team's merged answer to the owner's question: should pbrain become the tool our factory's agents learn with, holding **memories** and **docs**, and in what shape. It is the input to the functional spec. Nothing here is decided until the owner answers section 1.2.

Sources: the approved `project_overview.md`; the five independent positions in `research/positions/` (@architect, @architect-2, @lead-dev, @reviewer, @pm), each written before reading the others; the reviewed session-memory plan (#83, `docs/plans/session-memory.md`); the Mnemosyne research (#82) and the Hermes research (`research/hermes/`). No code was run for this proposal.

## 1. Recommendation

### 1.1 In one paragraph

**Build it, as a variant of the brainstorm.** The overview's two contexts stand: memory and docs, both first-class and distinct, memory first. All five positions add the same detail: inside those two contexts pbrain holds three classes of record and must keep them apart. A **memory** is what a person asked to have remembered or what an agent noticed: written cheaply, kept on this machine outside Git, labelled with who said it, who asked for it and when, and either **short-term** (ephemeral: it ages out in days) or **long-term** (kept until someone forgets it). A **document** is any Markdown file under a configured folder, found as it is. A **managed item** is today's decision, learning, observation, note or source, in Git, with an author, a status and a history. Agents get smarter through one loop: a person or an agent leaves a memory, the next agent recalls it, and what proves useful is **promoted** into a managed item or a document and reviewed in Git like any other change. Build memory first: explicit capture, then prompted checkpoints and re-injection for long sessions, measured for whether a later agent really does better before they are turned on by default. Then documents.

Two parts of the brainstorm change, and all five positions agree on both:

- **A memory does not hold a decision.** It can report one, as a claim with an author and a time. A decision gets its standing only as a managed item, because it needs someone who decided and someone who reviewed.
- **Explicit capture is the primary path, and "automatic" never means a recorder.** When a person says "remember that …", pbrain stores exactly that passage; when they say "take note of your last response", it stores that response byte for byte, with its time and context, as a long-term memory. Around that, a session that runs for days gets two automatic things: an optional short checkpoint the agent is asked for when it hands off a task, and a small page of the task's memories put back in front of it at start, on resume, when the task changes and after every context compaction. pbrain never harvests transcripts, writes nothing on an ordinary turn, and no background process writes memories, documents or skills.

- **Git is how knowledge reaches the rest of the team.** Memories stay on one machine. What should benefit a team working across machines is banked: promoted into a decision, a learning or a document in Git, reviewed, and from then on found by every clone with an empty memory. Several memories can be promoted together into one reviewed artifact that cites each of them. pbrain does not copy unreviewed memories between machines.

## 2. The model

| | Memory | Document | Managed item |
| --- | --- | --- | --- |
| What it is | Something a person asked to remember, or an agent's handoff, outcome or blocker from a task | Any Markdown file under a document folder | A decision, learning, observation, note or source |
| Written by | `pbrain store`: on a person's request, by an agent's own choice, or at a checkpoint prompt | Anyone, with any editor | `pbrain add` and `import`, or by hand |
| Kept in | Local state, outside Git | Git, where its author put it | Git, in the managed area (`docs/brain` today) |
| Identified by | A random memory id | Its folder and path, so a move changes it | Its file name, which pbrain never changes; a person who renames the file changes the id |
| Standing | *Said*: shown as who said it, who asked, when | None from pbrain: a file in Git, shown by path and line | *Banked*: author, status (provisional or verified), who decided, what it replaces |
| Lifetime | By its stored term. Short-term: days. Long-term: until forgotten or its chosen deadline | Until someone deletes the file | Until replaced; history kept |
| Review | None | Git review | Git review, and `check` |

**The loop.** `store` → `recall` → `promote` → Git review → found after a short-term memory has expired, by `search` for an item and by `docs search` for a document. A short-term memory that nobody promotes simply expires; a memory a person asked for stays, as a memory, until it is forgotten or reaches an expiry the person chose. Promoting it publishes a separate item or document, which may be an edited draft, and leaves the exact original where it was. Promotion is the bridge pbrain offers from a memory to something durable, and it takes an authored memory only: a typed report such as "check passed" is refused, as the #83 review settled. Anyone may still write an item of their own that cites the CI run directly.

**A third promotion target.** The Hermes research adds one thing to #83: a procedure (a how-to, a runbook) is neither a decision nor a learning, so an authored memory may also be promoted into a document. Section 5 has the rules: change an existing document before creating another, never overwrite a file that changed since it was read, and deliver through Git review.

### 2.1 What a memory promises

By @architect-2, in answer to the owner's question about the words local, attributed, expiring and advisory. "Expiring" has become two named terms, and "advisory" is dropped (section 2.2).

*Local* means one machine and OS user, with one enrolled brain shared across its linked worktrees. It gives offline operation and a bounded disclosure boundary. A different checkout of that brain can recall the handoff; a different clone, enrolled brain, user or host cannot. *Attributed* means a reader can distinguish the speaker, requester and recorder and find the original event. Storing a quotation faithfully establishes what was recorded, and nothing more; for a release or architectural decision, verify the cited evidence. *Short-term* and *long-term* are the two terms of memory, and the term is a property of each row. A user-directed “remember” is long-term, kept until explicit forget unless the person requests an expiry. Short-term memories, blockers included, have a seven-day lifetime and a count cap per task. A routine cache purge, an unrelated new write or a full store must never evict a long-term memory. Display the actual retention in the write receipt and in recall. Use bounded space and reject new long-term admissions at quota; forget continues to work at quota. Retention gives no extra decision standing, disclosure permission or guaranteed slot in the startup page.

### 2.2 The words we use

**Short-term and long-term.** These are the names a person sees. "Ephemeral" describes short-term in prose. In the reviewed #83 plan a short-term memory is a working row and a long-term memory is a retained row.

**"Said" against "banked".** The first draft called a memory "advisory"; the owner did not find the word meaningful, and does want the distinction between something an agent said and something the team has learned and checked. There are three rungs, and only the first two need a new word:

- **Said.** A memory: who said it, when, at whose request. "Said" is the owner's own word for it, fits a verbatim quotation as well as an agent's note, and claims nothing.
- **Banked.** A managed item in Git: someone wrote it up and committed it. That is all "banked" claims. pbrain cannot know whether a file went through review, and a banked item may be a provisional note, an imported source, which is always provisional, or a decision still in draft.
- **Verified.** The status an item already has when someone confirmed its content. It stays exactly as it is, with *provisional* beside it, and remains the only word pbrain uses for "checked".

"Established" is kept for prose, for the result of the whole workflow: banked, reviewed and verified. It is never a badge pbrain puts on a row, because pbrain cannot observe the review. This follows @lead-dev's objection to the previous draft, which had labelled every item "established".

Other pairs considered: *noted / banked* ("noted" is too close to the item kind `note`); *recorded observation / established knowledge* (@lead-dev: precise, long for a label on every row, and "established" has the problem above); *unreviewed / reviewed* (pbrain cannot know it, and it is wrong for a document).

The words appear where a new result is shown, never as a status to maintain, and no existing command's output changes: `Memory · said by architect-2 · 26 Nov · long-term · asked by the owner`, then the text; `Item · decision · verified · decided by the owner` and `Item · note · provisional`, with the kind and status an item has today; `Document · docs/runbooks/release.md:42`. A document gets neither word: it is reference material in Git, shown by its path. Promotion is how something said gets banked; neither a Git commit nor a verbatim match by that alone verifies a claim. One label stays as the #83 review settled it: a typed report such as a check result is shown as "Unverified: SOURCE reports …".

## 3. Documents

- **Finding them.** Each document folder is named in `pbrain.toml`. pbrain walks it for regular UTF-8 `.md` files, with today's guards: no symbolic links followed, Git-ignored files skipped, dot folders and pbrain's own data skipped, and no personal file ever reached by a shared walk. "Drop a file in and it is found" means `docs search` finds it lexically at once, and semantically after the next `docs sync` or bounded catch-up.
- **The folder decides what a file is.** A file under a document folder is a document. A file in the managed area is an item, under today's rules, including today's `check` findings for a broken one. A document that happens to carry `status: verified`, `decided:` or `replaces:` gains nothing from them. This is stricter than today's rule, where any Markdown with front matter under the brain is an item, and it is what keeps a stray header from granting standing.
- **Front matter.** None: the file is a document; its title is its first heading, else its file name. A well-formed header: pbrain may take `title` from it, to show and to search, and reads nothing else; the rest of a foreign header is not indexed, and the Markdown body is. A broken or unclosed header: the file is ordinary text from its first line. In every case line numbers count from the top of the file, and **pbrain never writes into a file it did not create**.
- **Identity.** A document is addressed by its folder's name and its path under it, in a form that can never collide with an item id. Two `README.md` files in different folders are two documents; today's stem ids would make them one ambiguous id. A rename changes the address, so a lasting citation belongs in a managed item or names a Git revision.
- **No standing, and no place in the item graph.** A document cannot replace or be replaced, has no status, and never appears in `prime`, which stays on managed items. Links between documents are ordinary Markdown links.
- **`docs check`.** A missing header is not a finding for a document. Document problems (unreadable, not UTF-8, over the size limit, two paths that differ only by case) are reported by `docs check`; plain `check` keeps reporting items only, with today's findings.
- **The managed area inside `docs/`.** Today's default brain is `docs/brain`, and its default personal section is `docs/brain/personal`; both lie inside the default document folder `docs/`. That layout must stay legal. The rule is that the sets of files actually walked are disjoint, not that the configured paths are: a managed area nested in a document folder is pruned whole from that folder's walk, with its personal section, before anything is read or counted, and its files are read once, as items. A shared document folder that reaches a personal path any other way, directly or through an alias, is refused. A test plants a private sentinel in the default layout.
- **Cost.** Lexical search needs no model. Semantic search does: on processors alone the default model embeds about 1.3 passages a second (measured for v0.5.0), so a wide folder is hours of first indexing without a GPU. That is the second reason enrolment is explicit and shows its inventory first.

## 4. Where state lives

By @architect-2.

| Resource | Identity and writes |
|---|---|
| Document or managed item | The checkout owns the original. Retain imported originals and the existing item/settings locks beside their protected files so older writers still serialize. |
| Derived shared SQL image and manifest | Use the guarded platform cache (including `PBRAIN_CACHE`). Isolate each selected brain **and checkout**. Check the configured roots, view, content coverage and embedding/chunker/writer profile before serving a generation. Put the publication lock beside its manifest. Two dirty linked worktrees on the same commit must be able to index different bytes at the same relative path. Compatible shared passage vectors and model bytes can still be reused. |
| Original team memories | Recommend owner-only, per-user **state** outside Git. Use an absolute `XDG_STATE_HOME` on Linux, otherwise `~/.local/state`, and `~/Library/Application Support` on Darwin, under `pbrain/.pbrain/memory/v1/<project-key>/`. The `.pbrain` component is deliberate: `import` and `--body-file` already refuse any input whose resolved path contains it, so a memory snapshot or a stale preview can never be read back in as content; a regression covers a direct and a symlinked attempt. Document the path that a supervisor or broker needs. Cache eviction then loses only rebuildable data. This revises #83’s cache placement. It does not change its bounded snapshot or guarded I/O design. |
| Personal data | Keep original personal memories and private derived data under the resolved personal root. Opening a shared view must never open a private snapshot, lock, vector or manifest, or expose its IDs, counts or timestamps. |

Resolve the **selected brain** first. In Git, key team memory by the canonical common directory plus the brain’s repository-relative path. This joins linked worktrees for one brain without joining other brains in that repository. An absolute external brain uses its own repository context, or its own canonical location outside Git. Neither branch, HEAD nor remote URL identifies an enrollment. Independent clones, users and machines remain separate. Validate the enrollment against the resolved roots on each open. An observed root replacement must fail closed pending re-enrollment; a new project placed at the same path must not silently inherit the old state. Include the originating task and, when supplied and visible, a revision as context for branch-specific observations. A check on one branch cannot establish the result on another.

Use a stable lock and one bounded snapshot per physical memory view. Serialize admission, replay lookup, expiry and atomic replacement through open directory handles; readers take a complete old or new snapshot. Retryable writes carry an event nonce and immutable observation time. Detect conflicting reuse, and bound content-free receipts so a late replay cannot resurrect a forgotten row. A model lease may remain warm between requests, but each request reopens its view, reads current state and releases its locks. Measure the worst-case rewrite cost with five concurrent agents before replacing this design with an append log or database. The supported sharing boundary is one OS user on one machine.

Who may write the state folder is part of the design, not only an install step. A person's own session and a manually run agent get write access to their enrolment's folder and to the cache. A restricted worker under automatic capture gets none: only the broker writes its enrolment, because a worker that could write the state directly could go round the broker's revocation. A test shows a revoked worker cannot store by writing the folder itself. pbrain writes nothing into Git's own metadata.

## 5. Memories and the learning loop

By @architect-2. It is the reviewed #83 plan in short form, with what the owner's wider goal, the Hermes research and the owner's input of 2026-11-26 (long sessions, explicit capture, provenance) change. The paragraph on what the host gives us is @architect's.

**Start with deliberate storage.** A memory can report a fact, a decision someone made, a blocker or a next action. It carries its provenance (below), scope, age, retention and optional task/session. Reviewed decision standing belongs to the Git item. For manual text, follow existing author resolution and show that the destination defaults to shared. Personal storage and retrieval require an explicit per-call choice. In a mixed session the agent must select the personal view for private material or abstain. For automatic shared prose, the broker always supplies a neutral enrolled actor label and source explicitly. It must never inherit Git account details, `PBRAIN_AUTHOR`, or raw personal/worktree paths into shared output.

**Capturing exactly what the user requested.** The primary path is a deliberate request. The host or skill proposes a selection; the broker resolves it to an original user-visible message and an exact UTF-8 span. For “remember that …”, use just the requested passage of the user message. For “take note of your last response”, select the immediately preceding complete, visible main-agent answer in this conversation and task. Preserve its text, Markdown, whitespace and line endings as delivered. Never regenerate it from the model’s recollection. A quotation *inside* a prompt, an example, a negation, hidden reasoning, a tool result or an unlabelled factory message supplies no user authorization. If the intended span or audience is unclear, ask once for the excerpt or destination; if the host no longer has the exact response, ask for a paste. Do not fetch another conversation or persist a transcript to make this work.

Use the same store handler for all routes. A qualified broker sends the exact bytes via bounded stdin plus a request nonce, context and explicit scope. The #80/#81 binding supplies the exact string as a field. A host may offer a “last response” shortcut; pbrain itself never guesses which session is current. Keep at most one last-visible-response handle or bounded volatile buffer per active session/task. An oversize response invalidates the previous handle; it must not accidentally select an older short reply. Proposed limits are 64 KiB of UTF-8 for deliberate verbatim capture and 2 KiB for an automatic checkpoint. Reject excess or a secret match in the body or metadata before writing a row, digest, log or tool notice containing the value. Never silently truncate, redact, Unicode-normalize or summarize. Unsafe input can be replaced with a newly selected, permissible excerpt. Do not print the selected body in the success receipt. A request to remember is not authorization to publish to the team. Respect per-call selection, enrollment, current context and the original message’s disclosure scope; offer an explicit personal save where appropriate. The broker must not accept worker-supplied requester=user as proof of a human request.

**Where the exact text comes from** (by @architect, with @architect-2's and @lead-dev's limits). Explicit capture has to work for a person with no factory, so pbrain supplies the adapter for a host it supports. Two sources, in order of preference: the host's own record of the conversation, read by the adapter at the moment of the request, which makes no new copy and needs nothing to run on a turn; and, for a host with no such access, a per-session helper that holds the one latest answer in memory, which needs an end-of-turn event and is not in the first version until qualified (until then, a paste). A staging slot on disk kept by pbrain is **not in the first version**: enabling explicit save must never start logging every answer, and a slot would do that. If it is ever added it is a separate opt-in, one size-checked and secret-scanned response in owner-only session state, outside recall and diagnostics, unreadable once its short fixed time is up, and removed at session end or the next open. When no source has the answer, `store --from-last-response` fails and asks for a paste; it never substitutes an older reply. Plain `pbrain store` always accepts exact text on standard input. A byte-for-byte match with its source is recorded as capture mode "verbatim" with a reference to the source message. It is never called "verified": that word stays with an item's status and a check's result.

**Recall and forget.** `recall --task N` can return a bounded page without search terms. Text recall begins with deterministic lexical matching, task/view filters, visible sources, recency and ID tie-breaks. Rank authored handoffs ahead of typed reports. Each typed check or delivery report carries its source and `verified: false`, even if submitted by a caller named factory. Preserve the label under truncation or omit the row. It never satisfies CI or review. Start the session with memories only; explicit recall can optionally request a separately labelled item/doc page under the same total budget. Keep their scores separate. Add semantic memory retrieval only after measuring paraphrase misses with a memory-specific cutoff. Forget affects subsequent requests immediately; it cannot redact a previous model input. Short-term rows live seven days, blockers included, and are capped by count per task (below), within 10,000 live rows per view. The routine lifetime and capacity eviction touch short-term rows only: never a long-term row, and never anything in Git. A long-term row ends only by an explicit forget or at an expiry the person asked for when saving it.

**Time, count, or both** (by @architect, in answer to the owner). Three ways to keep short-term memory from bloating:

- *Time only.* Simple, and it removes what is stale. It does nothing about one busy task or one talkative agent writing hundreds of notes inside a week.
- *Count only* (newest N per task or agent, oldest dropped). It bounds the bloat exactly, but a quiet task keeps a blocker from three months ago for ever, and a stale note misleads however few there are.
- *Both* (recommended). Seven days for every short-term memory, and the newest 32 per task, or per enrolled recording agent for a note with no task, inside hard row and byte limits per section. Whichever limit is reached first drops the oldest, by received time and then id. Surviving rows keep their observed time, and a dropped row leaves only the content-free receipt that stops a replay. A manual note with no task and no enrolled recording agent goes into one shared "unassigned" bucket per section, with the same cap. A claimed author name or an invented tag never opens a fresh budget, which is also why there are no buckets by caller-supplied tag in the first version.

Neither limit ever touches a long-term memory or anything in Git. The numbers are proposals: the pilot counts how many notes a task really collects in a week, and the cap is set from that.

**Long sessions.** On each user turn, act on an explicit request immediately. Main-agent Stop identifies the completed visible answer for a possible later request. Do not write an implicit row on every turn. There is one trigger for a checkpoint prompt: a task handoff reported by the supervisor, or an explicit checkpoint request. It is serviced once, at a suitable turn boundary, with one optional short, authored checkpoint in a qualified session. Idle may coincide with it and never supplies it. PreCompact settles already-authorized captures while the exact sources are available. It does not copy the compaction summary. On startup, resume, task switch and after context compaction, recheck enrollment, current view, forget/expiry and scope before re-injecting. Inject a fresh page, capped at three rows and 1,200 characters including provenance, once per task/context generation. On a host lacking a post-compaction injection hook, schedule the page for the next eligible turn; verify the hook sequence on each supported version. Direct recall can fetch more. Explicit long-term text can exceed the page limit: return a labelled preview and stable memory ID for a bounded, same-view full read. A preview must never be mistaken for the complete stored quotation.

**Plugin or configuration, per harness** (by @architect, with @lead-dev's reading of the hosts' documentation). pbrain has one entry point for every host: `pbrain hook EVENT --harness NAME`, which reads the host's event as JSON on standard input and answers in the form that host expects. What differs is how a host is told to call it.

So three hosts need only configuration and three need one small generated file each; none needs a plugin built and released apart from pbrain. Everything else is the same command.

- *What pbrain ships.* The manual commands and the skill, which work on every host with no hook at all. `pbrain hooks install --harness NAME`, for a project only: it shows the exact change first, keeps whatever configuration is already there, leaves the host's own trust prompt in place, and has a matching `uninstall` and `status`. Uninstall removes only pbrain's own entries and only if they are unchanged: a file nobody touched since the install comes back byte for byte, an unrelated edit made since is preserved, and a pbrain entry the user edited is reported as a conflict and left alone. Nothing is installed globally, and no skill edits a host's configuration by itself. The first version qualifies Claude Code; the others stay candidates until each is qualified on its own.
- *What the factory sets up.* After the team opts in, it adds the same hook entries to the per-member configuration it already generates at launch, and supplies what only a supervisor knows: the member's name, the task, the labelled team channel, the broker and the checkpoint request at a delivered handoff. pbrain decides what is admitted into memory.
- *Without any hook* an agent still has `store`, `recall` and the skill, and "remember that …" works; what needs a host's help is the exact previous answer, the task page after compaction, and the checkpoint.
- *Cost per turn.* Each configured event starts one `pbrain hook` process (about 4 ms to start today). In explicit-only use on a host that hands over the previous answer on request, or with a paste, nothing is configured to run at the end of a turn. A host with no such access uses the paste in the first version; the in-memory helper, which does need an end-of-turn event or the host's message stream, ships only after it is qualified and measured separately, including that an oversize answer invalidates the previous one and that nothing durable is written. With checkpoints on, the end of an ordinary turn runs the one bounded check described next.

**What runs on every turn, and what it may cost.** Nothing in this design asks the model anything on an ordinary turn. When a turn ends, the adapter does at most one local check: is a task handoff or an explicitly authorized action pending for this turn? On that path there is no model call, no prompt, no write to disk, no store lock, no database or index opened, no search, no transcript scan and no network request. Two callbacks must be told apart. The one that would remember the last answer is not needed at all where the host can hand over the previous answer on request. The checkpoint adapter's own end-of-turn check is a different one and may still run on a host whose checkpoint is built on the Stop hook; it is the inexpensive check just described, and it is what the budget below is about. The checkpoint prompt is the one thing that costs a model turn, and it fires once, when the supervisor reports a task handoff or someone asks for a checkpoint: not on a timer, not on idle alone, not on a retry, not on every turn. Proposed budget, to be measured and not yet measured: an ordinary end of turn adds at most 25 ms at the 95th percentile and 75 ms at the 99th over the same host with the adapter off, with pbrain's own command inside 10 ms at the 95th; a hook that overruns is abandoned and the turn goes on. For scale, starting the pbrain binary today takes 3.5 ms at the median and 3.9 ms at the 95th percentile (200 runs of `pbrain version` on the team's Linux machine, 2026-11-26, including about 1.6 ms of the measuring script's own cost); that is a start time, not a hook measurement.

**What can pause the automatic checkpoint, in plain words.** An automatic checkpoint is the one write that goes into team memory without anyone choosing its destination at that moment. So the supervisor allows it only for an agent whose whole context it can vouch for as team-visible. If that agent is handed something private, or something nobody labelled, the supervisor first switches off automatic team checkpoints for that agent's current context, because the agent might repeat the private text in its next summary. That is all that is switched off.

- *What still works for that agent:* its task, explicit `store` (with the destination chosen each time), personal saves, recall, and the task page.
- *How long:* until that agent starts from a clean context with a fresh grant. A new task number or a compaction does not lift it, because the private text can still be in the context or its summary. The same pane can host the clean context; no pane is switched off for good.
- *Who is affected:* only the agent that saw the input. **Typing into a pane does not revoke the team.**

An example from this factory. The owner types a confidential staffing note into the operator's pane. The operator goes on working and can save things explicitly, but its next automatic team checkpoint is withheld, so the note cannot be quoted into team memory. The operator then sends the members their assignments over the bus. Those messages are team-visible by the factory's own labelling, so the architect and the lead developer keep their automatic checkpoints. Had the owner typed the note straight into the architect's pane, only the architect's current context would be paused, until its next clean start.

Rethought for the owner's factory, where the owner types to the operator and the members mostly receive bus messages:

- *Members.* The supervisor labels the task channel and asks for the checkpoint when it delivers a handoff. A member that receives only labelled assignments keeps its automatic checkpoints through a session of any length.
- *A member's next task.* A fresh task can reuse the same pane with a new, isolated context and a new grant, which also clears a pause.
- *The operator, and any pane that mixes typed and labelled input.* It stays on explicit saves with the destination confirmed each time. The skill tells an agent to store a handoff when it reports a task, so the operator is reminded without anything being written unattended.

What the owner does to keep an agent's checkpoints running: give an ordinary assignment through the team channel, where the factory labels it team-visible before it is delivered. A clean member that receives only such assignments stays eligible. There is no standing setting that makes whatever is typed into a pane count as shared: the same input hook can carry the owner's keystrokes, a private message, scheduled automation or a forwarded paste, and a pane's name proves neither who sent a message nor who may read it. Nor can a label undo what came before: it cannot clean private text already in the context, make a private file read public, or turn a forwarded private message into an assignment. If a dedicated shared-only input channel is wanted later, it needs a visible scope, labelling and mediation before delivery, a positively identified source, a separate private route and a clean enrolment, and it is kept apart from an ordinary mixed pane. It could never override an earlier pause or make eligible a pane that has unmediated tools, history or input.

Three checks are separate and must not be confused: whether an agent may write an automatic team checkpoint (above); where an explicit save goes (chosen per call); and who may be shown a recall page (the recipient's own check, section 7).

**Which sessions get a checkpoint prompt.** Start with one qualified factory-managed worker. At that trigger (a task handoff the supervisor reported, or an explicit checkpoint command), prompt for at most one authored observation per changed task: its evidence, conditions and what the next agent should do. A session that runs for days gets one such prompt per task it finishes, not one at its end and never one per turn. Silence is a valid answer. Skip logs, inferred preferences, credentials, repeated rules and the hook’s own instructions. Before shared capture the supervisor must launch a fresh single-task worker with only known team-visible inputs and permitted filesystem access. Revoke eligibility before delivering private or unknown input, and recheck it at the broker write. Revocation is sticky: it survives a change of task and a compaction, since a summary can carry the private input forward, and only a genuinely fresh, isolated context with a clean input channel and a new grant qualifies again. Ordinary interactive panes and other hosts without this boundary retain manual commands. Validate all metadata and scan admitted text for secrets before persistence, diagnostics or embedding. A scanner cannot certify the audience of arbitrary prose.

The injected page is one frozen, quoted task page of at most three rows and 1,200 characters **including labels and citations**, per task and context generation. Quote each memory as an attributed lead. Check the cited source before treating its claim as established. Explicit later calls reread current state. Do not replay transcripts, infer durable user preferences, or let a timer rewrite a skill or doc. Hermes’s reported 21–66% costs were for its review process in particular cases. Charge all producer and consumer tokens to our own measurement.

**Provenance.**

| Context | Source and presentation |
|---|---|
| What/when | Record capture mode (user-selected span, prior response, authored checkpoint or typed report), original observation time, request time and pbrain’s received time; distinguish a missing original time from the server clock. |
| Who/from where | Record requester role (user/agent), recording member, original speaker, source session and message/turn, request message/turn, harness and available task. Use the factory enrollment and actual inbound event for a supervised worker. Manual CLI provenance is caller-claimed; absent values are explicitly unavailable. A factory relay arriving as a generic user-role API message does not by itself establish a human requester. |
| Model/runtime | Prefer the selected message’s effective model identifier and the turn’s configured thinking effort. Distinguish observed effective values from requested configuration; do not guess effective model, effort or a human display name. Capture no reasoning text. |
| Repository | Use the enrolled project alias and the selected checkout’s permitted branch/commit at the time of the observation. Use unknown for unavailable historical state. Never attribute the later checkout/model to an earlier answer. Branch names and provenance fields pass the same disclosure and secret checks as text. |

Compact recall should show age/time, speaker or member, requester, scope, retention and source alongside the excerpt. Detailed, same-view output returns the permitted fields with their origins (host-observed, pbrain-observed, caller-claimed or unavailable). Source claims are never an authority token. If a source cannot safely be labelled within the current disclosure boundary, refuse the shared write or omit the row, including from injected text.

**What the host gives us.** Checked against the Claude Code hooks reference on 2026-11-26; each supported host and version still needs its own qualification. A Stop hook receives the turn's final visible answer (`last_assistant_message`) and its effort level, and is the continuation point chosen for the Claude Code checkpoint: a Stop hook can block, so the turn continues and the agent can write. A PreCompact hook cannot: its output becomes instructions for the compaction summary, so it is used to settle a pending explicit save and to keep the task number in the summary. SessionStart fires again with source `compact` after a compaction, and with `resume` and `fork`, and carries the model identifier when the host has it. UserPromptSubmit also fires for messages from other sessions, background agents and scheduled tasks, and does not say who typed the prompt. So the origin of a prompt fails to **unknown**, inside a factory pane and outside one: a prompt that the factory did not deliver may still be automation or another adapter. The requester is recorded as a person only when the integration positively identifies direct interactive input; otherwise it is unknown or claimed, and the agent asks the person to confirm before anything is kept until forgotten or shared on their word. That confirmation counts only if it arrives through a positively identified human action. So model and effort are read from the host, never from the agent's own account of itself. "Observed" in the table below means reported by the installed adapter; on one user's machine pbrain cannot authenticate that, as it cannot for typed reports.

**Promote authored knowledge.** Inspect the evidence, preserve its source citation in the proposed text, search existing knowledge, and preview the complete proposed change and target in the selected checkout. For a learning or decision, freeze exact Markdown bytes and use #83’s memory-then-item lock order, durable spent-token barrier and exclusive publication. Ordinary Git review accepts a shared change. Refuse every typed report before preview, token or publication; a durable statement about a check should cite the actual run. Private-to-shared promotion is forbidden. Once docs have guarded roots and addresses, a procedure can also become a new doc or a proposed update to an existing doc in the same view. Create a new file exclusively. For an update return a reviewable patch tied to the old bytes’ digest. A changed base needs a new preview. Other Markdown editors need not honor a pbrain lock, so v1 must never silently replace the live target after a stat/hash check. No hook can confirm, install a skill or delete reviewed material.

**Several memories into one artifact.** `pbrain promote MEM_ID MEM_ID …` turns a bounded set of authored memories into a single document, learning or decision. The author writes the consolidated text; pbrain does not summarize. It is one proposal: one section, one frozen set of sources, one preview, one token, one reviewed change. The artifact carries, for every source, a citation a teammate can use on their own clone: who said it, who asked, when, and the evidence it pointed to. A machine-local memory id alone is not a citation, since it means nothing on another machine. A source with nothing portable to cite must either point to a shareable source or contribute a deliberately chosen excerpt that the reviewer sees in the artifact; otherwise the proposal is refused. The #83 guarantees for retry and crash hold for the group as they do for one memory: one token per artifact, spent durably before publication, and a replay publishes nothing twice. Two cases differ. Before the first publication, a forgotten source invalidates the whole frozen proposal and no artifact appears. After publication, a lost reply followed by a forget and an identical confirm can neither publish again, nor delete the artifact, nor bring the source back: a retry that is still authorized may acknowledge the matching published artifact from the token's bounded receipt, and if that cannot be reconciled safely it returns an indeterminate result without another write. At confirmation, before the first publication, every source and the target are checked again, and the whole proposal is refused if any source has been forgotten, has expired, is private for this target, or is a typed report. The original memories stay as they are.

**Across machines.** Each machine keeps its own short-term and long-term memories. Git carries what the team shares: machines A and B can each propose cited contributions to the same document, and machine C pulls it and uses it with an empty memory. pbrain never runs a Git command that changes a repository, so a banked artifact reaches the team when someone commits and pushes it through the usual review. Copying unreviewed memories between hosts is refused for the first version, for three reasons: the reader, the expiry and the forget of a memory would all have to be enforced on machines pbrain does not control, and a forgotten or private note cannot be called back from a remote copy; identities and conflicts across users need rules that one user on one machine does not; and it is not yet shown that Git plus the factory's own addressed handoff for urgent work leaves a gap. If the owner needs agents on two machines to see each other's notes before any review, that is a distinct requirement and should be named as one.

## 6. Commands and compatibility

- **What stays exactly as it is.** Every item command that exists today (`search`, `get`, `list`, `prime`, `add`, `verify`, `import`, `check`, `sync` and the rest) keeps its name, flags, ids, JSON, error codes, exit codes and **result set**: the same invocation on the same brain returns what it returns today, whether or not a document folder has been enrolled. The tool names and meanings in the #80 catalog are those commands and do not change. A brain with no document folder enrolled behaves exactly as today in every respect.
- **New, for memory:** `pbrain store`, `recall`, `forget`, `promote`, as #83 has them, with additions from the owner's input. `store` takes the term (`--retention short-term|long-term`, with `--until DATE` for a chosen end; the spelling is open in section 12), and `promote` takes several memory ids for one artifact. `store` takes exact text on standard input and keeps it byte for byte; `store --from-last-response` is the shortcut a supported host's adapter makes available; and a full, same-section read of one memory by its id, because a long-term quotation can be longer than a recall page shows. A tool call passes the same text as a field.
- **New, for documents:** `pbrain docs search`, `docs get` and `docs list`, whose results hold documents and managed items, each labelled; and `pbrain docs sync` and `docs check`, which build the document index and report document problems. Plain `sync` (with `sync --status`) and `check`, and their #80 tools, stay on managed items even after a folder is enrolled, so enrolment never changes what they report. Whatever the index is underneath, the two sides show their own readiness, counts, notices and errors: a `docs sync` never makes an unbuilt item index look ready. All five are new commands with new result shapes, so they are new catalog tools; nothing is renamed and no operation is listed twice. `pbrain docs add` is the brainstorm's spelling of `add`: it writes a managed item, and the catalog lists that operation once. A file dropped into a document folder needs no command at all.
- **New, for hosts:** `pbrain hook EVENT --harness NAME`, the one command every host calls, and `pbrain hooks install`, `uninstall` and `status` for one project (section 5). Neither is a tool an agent calls, so neither is in the tool catalog.
- **Memory and documents are not mixed.** `recall` returns memories. A caller that wants both asks for both and gets two labelled pages under one size limit, never one merged ranking. A document search never slips a memory into its results.
- **No rename dependency on #80.** The catalog's rule is that a released tool is never renamed. This proposal only adds names, so it imposes no technical rename dependency on #80. The #80 pilot and #81 stay paused until @operator releases them.
- **Later, not now:** whether a next major version folds top-level `search`, `get` and `list` into the `docs` group. Until then an agent sees two search tools, and the skill has to say which to use (section 11).

## 7. How an agent finds it

- **The skill** stays the one place that says how to use pbrain: when to recall, when to store, what to cite, when to propose something durable. It also says how to act on "remember that …" and "take note of your last response": store that exact text at once, ask when the passage, the destination or the person asking is unclear, and never rewrite it from memory. The capture rules from the Hermes research go into it and into the handoff prompt: lessons, not logs; only what this session actually showed, with a source the next agent can check; one lesson is one rule, so fix the existing one; nothing inferred about a person; no claim that a tool does not work; an empty answer is a good answer.
- **How a result shows what it is.** By its class and one word (section 2.2): a `Memory` is *said*, with who said it, who asked, when and its term; a managed item is *banked* and shows the kind and status it has today; a `Document` is shown by path and line. A typed report keeps "Unverified: SOURCE reports …".
- **The task page.** One frozen page of memories for the task: at most three rows and 1,200 characters, each row with its source and age, quoted as an attributed lead: the agent checks the cited source before treating the claim as established, and never takes a row as an instruction. It is put in front of the agent at start, on resume, when the task changes and after a context compaction, once per task and context, read fresh each time so that a forgotten or expired row never comes back. Reading has its own check: the page goes only to a trusted, enrolled recipient whose section is rechecked each time; an unknown recipient gets no page, and personal rows are injected only where that injection was explicitly authorized. A long-term memory has no reserved place on it. Memory only at first; whether top document hits should join it is for the evaluation to answer, as a separate condition.
- **`BRAIN.md` (D12).** Optional, written and owned by a person, never touched by pbrain after it is created. It only helps if the harness's own instruction file (`AGENTS.md`, `CLAUDE.md`) points at it or at the skill, because no harness loads `BRAIN.md` by itself; `init` can print those lines for a person to paste. @reviewer would measure its token cost and whether it prevents wrong calls before recommending it to users.

## 8. Build order, and what we refuse

1. **Explicit memory.** `store`, `recall`, `forget` across two worktrees: exact text in, short-term or long-term retention, provenance on every row, and the skill's handling of "remember that …". Proved on concurrency, replay, expiry, a long-term row surviving expiry and a cache purge, refusal of oversize and secret-bearing text, and that adding private data changes nothing a shared read returns. Then the adapter for one host, so that "remember your last response" works without a paste.
2. **Promotion** of an authored memory into a managed item, then of several memories into one, once publication and replay faults are tested. This is what makes memory useful to a team on more than one machine, so it follows step 1 directly.
3. **Long sessions.** The task page re-injected at start, resume, task change and after compaction; then the optional checkpoint at a task handoff, in a session that qualifies. Built and qualified per host, in the factory repository where the factory is the supervisor, then evaluated (section 9) against the skill and today's items alone. On by default only after that passes.
4. **Documents.** Opt-in folders, path addresses, `docs search/get/list` and `docs sync/check`, the index moved to the per-checkout cache. Proved against a frozen fixture of today's behaviour, plus files with no header, foreign and broken headers, equal file names, rename and delete, long documents with the evidence near the end, two worktrees at different commits, and private, ignored and linked sentinels. Then promotion into a document.

Steps 3 and 4 do not depend on each other. This order is @lead-dev's and @reviewer's and follows the owner's "memory first"; @architect-2 and @pm would do documents before the automatic part. If two people are free they can run side by side, since step 3 is mostly work in the factory repository.

**Refused**, by every position that mentions it: treating plain Markdown as a managed item; treating an agent's memory that nobody promoted as a managed item; results that silently mix memories, documents and items, or that hide a lower-authority observation inside a document result; rewriting people's documents or filling in front matter; keeping originals or reviewed knowledge in a cache or database; harvesting transcripts, tool output or direct messages; a memory written on every turn; a copy of every answer kept on disk in case someone asks to remember it; taking a prompt of unknown origin as the person's word; cutting, redacting or summarizing text that was to be kept verbatim; a periodic background writer; shared memory from a mixed or private session; promoting a typed report; a memory satisfying a release or review gate; automatic skill creation or edits without a diff and Git review; a required remote service or LLM summarizer; copying unreviewed memories across machines or accounts; a generated memory file in Git; deleting anything a person reviewed; letting how often something was read change its rank; indexing a whole repository by default.

## 9. Acceptance and measurement

By @architect-2, with the measures @pm and @reviewer asked for.

1. **Correctness before agents.** On Linux and macOS, two linked worktrees with different dirty versions of the same managed item, read with today's search, must return checkout-correct text and line citations while sharing exactly one eligible task memory. Once the documents slice has landed, a separate condition can test document hits in the startup snapshot without changing the base comparison.
3. **Proposed pilot gates.** Require zero observed private/secret leaks, zero unauthorized promotions and no increase in mistaken durable decisions. Manual memory is scored against the same control and reported separately; it does not gate the default. Report inconclusive results as such. At capacity, measure write amplification and producer delay under five agents and report p50/p95 latency and target p95 warm lexical recall under 100 ms on a named quiet host. With that slice comes a compatibility gate: run matched managed-item fixtures with a fixed clock and ids, one of them with an enrolled document folder holding a valid document and an invalid-UTF-8 `.md` file. Plain `check` and `sync`, from the CLI and through the catalog, must give the same output, findings, exit code and item counts on both; only `docs check` reports the bad file, and `docs sync` accounts for the valid one. Preserve document quality as a separate release gate, applied when the documents slice lands: retain the frozen retrieval/abstention baseline and add long, unmanaged documents with late evidence, duplicate basenames and malformed/foreign headers. Verify grounding, citations, rename/delete freshness, model-free lexical discovery and cost to index added roots. Any paid agent runs require owner approval.

4. **Acceptance before a long-session pilot.** Use synthetic multi-day event sequences with two agents and two worktrees: capture only the “remember that” span of a longer prompt; preserve a multi-paragraph prior response byte-for-byte and distinguish its agent author from its human requester. Cross a model switch, branch change and compaction and check the original metadata. Interleave two sessions; replay a request or duplicate hook; run Stop for ordinary turns and a tool failure. Require no save for an ambiguous, quoted or negated instruction, an absent/oversize last response, secret-bearing text or a tainted shared source. Show no persisted body or content-bearing error on refusal. Forget or expire a row just before re-injection and ensure it does not recur. A long-term row survives 15 days, restart, quota pressure and cache purge, then disappears on explicit forget. A second long-term row with an expiry its requester chose stays through the same pressure and disappears at that deadline, not before. A short-term row expires on schedule, a blocker included, at seven days. Write past the per-task cap inside a day and require the oldest to be dropped by received time, the survivors to keep their observed times, a long-term row in the same task to stay, and a replay of a dropped row to be refused. Alternate 33 no-task writes across two worktrees under different claimed author names with no enrolled recorder, and require only the newest 32 to remain and the personal snapshot to be untouched. Promote an edited draft of a long-term memory, then read the exact original back unchanged. Charge all automatic prompts, checkpoints and reinjections to the automatic condition. Use the same explicit-remember requests in the manual and automatic arms to isolate the incremental value of hooks, leaving the no-memory control and predeclared safety/rollout gates intact. Add: revoke a session, then change its task and compact it, and require that no shared checkpoint is admitted afterwards; a human directive with a quoted payload ("remember this exact quote: …") saves the quote verbatim, while the same instruction appearing inside quoted or pasted content saves nothing; a prompt of unknown origin never yields a row whose requester is a person, and a second unlabelled "yes" does not confirm it: the confirmation must itself come through a positively identified human action; a missing or dead helper makes `--from-last-response` fail, never return an older reply; and enabling explicit save alone creates no additional copy of an answer on disk, in pbrain's or the adapter's state or logs (the host's own conversation record, which section 5 reuses, is not pbrain's). The staging slot is not in the first version, so no test may find one. Hook overhead: compare 1,000 matched ordinary ends of turn, with small and 64 KiB answers, on Linux and macOS, with the adapter off and with it on and the checkpoint feature enabled but no handoff eligible, so that the real end-of-turn check is what is timed, including the real adapter launch; report the 50th, 95th and 99th percentiles against the budget in section 5 and show zero durable writes, zero model calls and zero prompts on that path; a hook that overruns its limit is abandoned and the turn completes. Labels: in any new output that shows more than one class, a provisional note, an imported source and a verified decision appear with their existing kind and status beside a memory marked said and a typed report marked unverified, and no existing command's output changes. Setup: `pbrain hooks install` on a project with existing host configuration shows its change and preserves every other setting; `uninstall` restores an untouched file byte for byte, keeps an unrelated edit made after the install while removing pbrain's own unchanged entries, and reports a conflict for a pbrain entry the user edited; with no hook installed, the manual commands and "remember that …" still work. Exactly one eligible handoff prompts; idle, retries and unrelated ends of turn do not repeat it. Consolidation: promote three authored memories into one document and read each citation on a second clone with no memory; forget one source between preview and confirm and require the whole proposal to be refused; the invariant under every fault is at most one artifact; with no fault, run two confirms at once and require exactly one artifact and one spent token; crash after the token is durably spent but before the item's commit point, and require no artifact and an indeterminate retry that writes nothing; lose the reply after the item's commit point, forget a source and confirm again, and require exactly one artifact, no second write, no deleted artifact and no recreated source; give one source nothing portable to cite and require a shareable source or a reviewed excerpt, else refusal; include one typed report, or one personal source in a proposal whose target is shared, and require the same (a wholly personal proposal into a personal target is allowed). Across machines: machine C, with an empty memory, finds the banked artifact after a pull and resolves its durable references, such as a commit and path or a CI run it can open; a machine-local memory id does not count as one. The pause rule, four cases: an assignment labelled on the team channel leaves its receiver eligible; unmarked confidential input typed into the operator's pane withholds only the operator's automatic team checkpoint and leaves its explicit saves working; the same pane after a compaction is still paused; a clean worker that received only the assignment still checkpoints; and a delivery that mixes a labelled assignment with unlabelled text, or whose source is unknown, pauses its receiver.

## 10. Disagreements

Each is stated with who holds which side. The recommendation in section 1.2 is the first side listed.

1. **Order (D4).** Memory first, including the automatic handoff, then documents: the owner's order as @lead-dev and @reviewer lay it out, joined by @architect. Memory by hand, then documents, then the handoff: @architect-2. Documents first: @pm, because a document's source is in Git and its freshness is easier to prove; @pm accepts memory first and asks that document search not regress meanwhile.
2. **`./docs` by default (D8).** Default for new projects only, explicit enrolment for existing brains: @architect-2, @lead-dev, and @pm in substance ("only after an explicit sync or migration step"). Opt-in everywhere, no default at all: @architect's first position, withdrawn in favour of the above. Default for every project: the brainstorm; nobody on the team holds it.
3. **Front matter in documents (D9).** The folder decides, and a plain header may give a title: @architect-2 and @lead-dev (who would also take validated tags), joined by @architect. Read only a versioned `pbrain:` block and nothing from foreign headers: @pm and @reviewer. The two sides agree on everything that carries risk: no standing, links or author from a document's header, and no writing. They differ on whether `title:` in a Jekyll or Hugo header may be shown. Recommended: title only, and keep the name `pbrain:` reserved for the day a document needs tags or anything more.
4. **A header that changes a file's section.** Never; the folder and Git placement decide who may read a file: @architect, @architect-2, @lead-dev, @reviewer. A valid `pbrain:` block may mark a document shared or personal, and a broken one hides the file: @pm. The objection: a file under a tracked shared folder is already in everyone's clone, so a header that says "personal" promises a privacy pbrain cannot give.
5. **Where memories are kept (D5).** A state folder: @architect-2 and @lead-dev, joined by @architect. The cache: @pm, and #83 as it was reviewed. @reviewer accepts either if a cache's loss on purge is stated to users.
6. **Default section of `store` (D14).** Shared unless `--personal` is given, as #83 was reviewed: @architect, @architect-2, @lead-dev. Personal by default, shared on request: @pm, as the safer default. Note that "shared" here reaches one user's agents on one machine, which is far less than a shared item reaches.
7. **A `docs` command group (D11).** Add it, beside unchanged commands: the owner's brainstorm, @architect-2, @lead-dev, @pm, @reviewer. Flat verbs only: @architect's first position, withdrawn. Its worry was that #80's catalog forbids renaming a released tool; an additive group renames nothing. What remains of the worry is the cost of two search tools side by side.
8. **`recall` over memories and items together.** Separate labelled pages, never one ranking: @architect-2, @lead-dev, @pm, @reviewer. One mixed answer, items first: @architect's first position, withdrawn.
9. **Overlapping folders.** Settled during the merge, and the exception is the merge's own. @architect-2 and @lead-dev each wrote that overlapping folders should be refused at first. The default layout needs one exception, the managed area nested inside a document folder, and both now support it on the condition in section 3: the document walk and the managed walk are disjoint, the nested `docs/brain` is pruned together with its personal section, and every other overlap is refused.
10. **When the automatic checkpoint may exist.** Build and qualify it, default off until the evaluation passes: @architect-2, @lead-dev, @reviewer, @architect. Not until a 24-task privacy and freshness pilot has run on explicit memory: @pm.

11. **Who keeps the last response.** Raised by the owner's input and settled in the merge. @architect first proposed that pbrain keep a per-session slot on disk fed by every Stop. @architect-2 and @lead-dev objected that this would collect private and secret-bearing answers before anyone asked to remember one, and strand them when a session is killed. The text in section 5 is the result: the host's own record or a volatile helper, and no pbrain slot on disk in the first version (@architect-2's recommendation after the owner asked what runs on every turn).
12. **Whether a prompt with no known sender is the person.** @architect first wrote that outside a factory a prompt is the user's. @architect-2 and @lead-dev: origin fails to unknown everywhere, and only a positively identified interactive input counts as a person. @architect has withdrawn; section 5 has their rule.

13. **A standing "typed here is shared" setting.** @architect proposed that the owner could declare a pane's typed input team-visible by default, so that the operator's own checkpoints keep running. @architect-2 declined it for the first version: one input hook carries keystrokes, private messages, automation and pasted forwards alike, and a pane's name proves neither origin nor audience. @architect has withdrawn it; section 5 has the labelled team channel in its place.

## 11. Risks

- **Dilution.** A long tree of prose and a stream of unreviewed memories can bury the few items with standing. Labels are agreed; how `docs search` orders items against documents is not yet designed and must not make today's fixture worse.
- **A wrong memory, repeated.** Five agents recalling one mistaken handoff make five mistakes. The brakes are expiry of short-term memories, the "unverified" label, quoting recalled text as a lead to check, and review at promotion.
- **Nothing is live across machines.** A teammate on another machine sees a note only after it is banked in Git and pulled. That is the price of not copying unreviewed text between hosts.
- **Long-term memories pile up.** What a person asked to remember never ages out, so a stale one stays until someone forgets it. A verbatim answer is kept with its mistakes. The brakes are the quota that refuses new ones, the age and source on every row, no reserved place on the task page, and a listing of long-term memories for a person to prune.
- **Leaks.** A personal note enrolled into a shared folder by accident; a secret in a handoff; an author name taken from a private environment. Secret scanning helps and is not the boundary; the boundary is which folders and sessions are admitted at all.
- **Stale or crossed indexes** between worktrees, and stale citations after a file moves.
- **Indexing cost** without a GPU once folders are wide, and slower scans on every read.
- **Context cost.** The start page, a second search tool and a `BRAIN.md` all spend tokens on every session. Hermes reports 21 to 66 percent more input tokens for its loop; that is a warning to measure ours, not an estimate of it.
- **Two identities in one tool:** file-name ids for items, path addresses for documents.
- **Scope.** This is at least four deliveries (memory, promotion, documents, the factory adapter), with work in the factory repository, on top of #80's pilot and #81, which wait.
