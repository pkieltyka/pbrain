# Agent memory systems: how each one models and maintains memory

Researched 2026-11-19 by @lead-dev-2. Hermes is summarised from factory's earlier study, not re-read. "Inference:" marks my reading. Benchmark numbers are as their authors report them; most come from vendors evaluating their own systems.

## Hermes agent (Nous Research): see factory#89

Factory's study of `NousResearch/hermes-agent` at commit `c152cfceec` is in [factory#89 comment](https://github.com/pkieltyka/factory/issues/89#issuecomment-7010508618) (architect, reviewed by lead-dev). The points that matter here:
- **Three stores.** `MEMORY.md` and `USER.md` are capped at 2,200 and 1,375 characters and frozen into the system prompt at session start ("preserving the prefix cache", about 1,300 tokens). Skills are procedural memory, with only an index of names and ≤60-character descriptions in the prompt. Raw session history sits in SQLite FTS and is searched on demand.
- **Writes**: by the model at any time, plus a background review every 10 user turns or 10 tool iterations. Memory writes are scanned for injection, exfiltration and secrets, and scanned again on load. The unattended review may *add* memory but its patches and removals are staged for user approval.
- **Staleness**: memory entries never expire. Skills have usage counters: stale after 14 unused days, archived (never deleted) after 30.
- Hermes now also supports one external memory provider at a time (RetainDB and ByteRover bundled; Honcho, Hindsight, Supermemory, mem0 and others from a catalogue), "the built-in memory is always active alongside it" ([Memory Providers](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory-providers)).
- #89's conclusion for pbrain: adopt a usage signal (retrieval counts in the derived index, a candidate list only), scanning at write time, and a frozen, size-bounded session slice. Reject unattended agent writes and pressure to save.

## Zep / Graphiti: bi-temporal knowledge graph

- **Paper**: Rasmussen et al., "Zep: A Temporal Knowledge Graph Architecture for Agent Memory", [arXiv 2501.13956](https://arxiv.org/abs/2501.13956), 2025-01-20. Graphiti is the open-source engine ([README](https://raw.githubusercontent.com/getzep/graphiti/main/README.md)). It needs Neo4j, FalkorDB or Neptune, plus an LLM ("defaults to OpenAI") and an embedder.
- **Bi-temporal model** ([§2.2.3, HTML](https://arxiv.org/html/2501.13956)): "the system tracks four timestamps: t′created and t′expired ∈ T′ monitor when facts are created or invalidated in the system, while t_valid and t_invalid ∈ T track the temporal range during which facts held true. These temporal data points are stored on edges".
- **Invalidation on contradiction**: "The system employs an LLM to compare new edges against semantically related existing edges to identify potential contradictions. When the system identifies temporally overlapping contradictions, it invalidates the affected edges by setting their t_invalid to the t_valid of the invalidating edge. Following the transactional timeline T′, Graphiti consistently prioritizes new information". README: "When information changes, old facts are invalidated — not deleted. Query what's true now, or what was true at any point in time."
- **Reported results**: DMR 94.8% vs MemGPT 93.4%; on LongMemEval "accuracy improvements of up to 18.5% while simultaneously reducing response latency by 90%". These are vendor-reported.
- **For pbrain (inference).** Separating *when it was true* from *when we recorded it* is the right model. The trigger to copy is not "an LLM decides on every write" but "newest wins". Factory's rule is the opposite: "freshness alone does not replace" a decision. A bi-temporal graph also needs a graph database, an LLM on every write, and embeddings.

## mem0: from LLM-chosen UPDATE/DELETE to add-only

- **Paper** ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413), 2025-04-28): extraction, then an update phase in which, for each candidate fact, the top 10 similar memories go to the LLM, which picks "ADD … UPDATE for augmentation of existing memories with complementary information; DELETE for removal of memories contradicted by new information; and NOOP". The graph variant (Mem0^g) instead marks conflicting relations "as invalid rather than physically removing them to enable temporal reasoning". Reported on LoCoMo: "26% relative improvements in the LLM-as-a-Judge metric over OpenAI" and "more than 90% token cost" saved against full context (vendor-reported).
- **Platform v3 algorithm** ([migration guide](https://docs.mem0.ai/migration/platform-v2-to-v3.md)) reverses that design: "Memory mutations | ADD, UPDATE, DELETE | ADD only: nothing is overwritten or deleted". "When information changes (e.g., a user moves from New York to San Francisco), both facts are preserved with temporal context". "If your application previously relied on UPDATE/DELETE behavior to keep memory counts low, the new algorithm handles this at retrieval time instead. Multi-signal retrieval ranks the most relevant, current information higher without destroying historical context."
- **Expiration** ([Memory Expiration](https://docs.mem0.ai/platform/features/memory-expiration.md)): `expiration_date` (UTC date) "hides a memory, it does not delete it". `search()` and `get_all()` skip it, "fetching it by ID still returns it". "Malformed dates fail open: … A bad date never makes a memory silently vanish."
- **For pbrain (inference).** A leading vendor moved from LLM-driven overwrite and delete to append-only storage with resolution at read time. That matches factory's "supersede a stale note instead of rewriting it" and pbrain's "superseded items hidden by default, history on request". Hide-but-get-by-id is the right default for supersession too.

## Letta (formerly MemGPT): from memory blocks to Git-backed MemFS

- **MemGPT** ([arXiv 2310.08560](https://arxiv.org/abs/2310.08560), 2023): an OS analogy. Main context (system instructions, a "fixed-size read/write block" of working context, a FIFO message queue) and external context (recall storage of messages, archival storage of arbitrary text). On a "memory pressure" warning at about 70% of the window, the model moves facts out to working context or archival storage.
- **Letta Code today** ([MemFS](https://docs.letta.com/concepts/memfs/index.md); [Context Repositories, 2026-02-12](https://www.letta.com/blog/context-repositories)): memory is "held in a git repository that belongs to the agent". Each memory is "Markdown with YAML frontmatter" (`name`, `description`). "Files at the memory root are loaded into the agent's system prompt on every turn" (older agents: `system/`). Directories with their own `MEMORY.md` index "stay out of context until they are needed". "Every memory edit is committed". "Memory subagents such as dreaming and memory doctor use git worktrees so they can update memory concurrently without blocking the main agent." Search: "MemFS does not include a semantic or vector index by default"; an optional mod adds keyword search, and "Semantic and hybrid modes require [QMD](https://github.com/tobi/qmd)".
- **Multi-agent sharing** ([Shared memory](https://docs.letta.com/concepts/shared-memory/index.md)): a shared repository owned by the organisation, cloned beside each agent's MemFS. "The agent must commit and push its changes. Other agents can then pull those commits". Cloud-only. "self-hosted deployments can share memory by pointing agents at their own git remote" ([SDK memory](https://docs.letta.com/agent-sdk/memory/index.md)).
- **Dreaming** ([Memory & dreaming](https://docs.letta.com/configuration/memory/index.md)): background subagents review recent conversations and update memory. The option "Agent reviews before applying … does not ask you for approval". `/doctor` audits "placement, duplication, and system-prompt token usage". Cloud quota: 5 MiB per memory repository on Free, 50 MiB on Pro.
- **For pbrain (inference).** This is the closest prior art to pbrain's storage choice: Markdown with front matter in Git, `description`-gated progressive disclosure, worktrees for concurrent writers, and qmd as an optional search layer. It differs on authority: the agent owns and rewrites its own memory, with no supersession or review by a human. Letta's blog does describe "git-based conflict resolution" between memory subagents, but gives no data on how often merges conflict.

## A-MEM: Zettelkasten-style agentic memory

[arXiv 2502.12110](https://arxiv.org/abs/2502.12110) (2025-02-17): each new memory becomes a note with "contextual descriptions, keywords, and tags". The system "analyzes historical memories to identify relevant connections, establishing links", and "memory evolution" lets new memories "trigger updates to the contextual representations and attributes of existing historical memories". Inference: link suggestion is a cheap, useful idea (pbrain could propose `relates` links at add time). Rewriting old notes automatically conflicts with "supersede, don't rewrite" and with Git-friendly append-only writes.

## ACE (Agentic Context Engineering): itemised playbooks with counters

[arXiv 2510.04618](https://arxiv.org/abs/2510.04618) (ICLR 2026):
- **The problem it names**: "context collapse … when an LLM is tasked with fully rewriting the accumulated context at each adaptation step". In their AppWorld case study, "at step 60 the context contained 18,282 tokens and achieved an accuracy of 66.7, but at the very next step it collapsed to just 122 tokens, with accuracy dropping to 57.1—worse than the baseline accuracy of 63.7 without adaptation."
- **Its fix**: context as "structured, itemized bullets", each with "a unique identifier and counters tracking how often it was marked helpful or harmful". Updates are "compact delta entries, which are merged deterministically into the existing context by lightweight, non-LLM logic", so "multiple deltas can be merged in parallel". Grow-and-refine: "bullets with new identifiers are appended, while existing bullets are updated in place (e.g., incrementing counters). A de-duplication step then prunes redundancy by comparing bullets via semantic embeddings."
- **For pbrain (inference).** This is strong evidence against letting a model rewrite or summarise the store, and for small items with ids, append-only deltas and deterministic merges, which is what one-file-per-item in Git gives. Its helpful/harmful counters are a usage signal that belongs in the derived index, not the files.

## Generative Agents: recency × importance × relevance

[arXiv 2304.03442](https://arxiv.org/abs/2304.03442) (Park et al., 2023): retrieval score = α·recency + α·importance + α·relevance, each min-max normalised, "all αs are set to 1". Recency is "exponential decay … since the memory was last retrieved. Our decay factor is 0.995". Importance comes from an LLM 1–10 "poignancy" rating at write time. "The top-ranked memories that fit within the language model's context window are included". Reflections are generated "when the sum of the importance scores for the latest events … exceeds a threshold (150)". Inference: this is the classic weighting formula. For pbrain, authority and status should gate what is eligible *before* any such score. Recency of retrieval is a usage signal the index can keep.

## Claude Code auto memory, Claude memory tool, Codex memories, Cursor journal

(Layouts are in [../markdown-knowledge-stores/agent-memory-files.md](../markdown-knowledge-stores/agent-memory-files.md).)
- **Claude Code auto memory** ([docs](https://code.claude.com/docs/en/memory)): four types (`user`, `feedback`, `project`, `reference`), skips "anything it can derive from the codebase". `MEMORY.md` index loaded up to 200 lines or 25 KB; topic files read on demand; machine-local.
- **Claude memory tool (API)** ([docs](https://docs.claude.com/en/docs/agents-and-tools/tool-use/memory-tool)): client-side file commands under `/memories` (view, create, str_replace, insert, delete, rename). "Claude automatically checks its memory directory before starting a task." Security guidance: strip sensitive data, cap file sizes and `view` output, "Periodically delete memory files that haven't been accessed in a long time", and path-traversal checks.
- **Codex memories** ([docs](https://developers.openai.com/codex/memories)): background generation from idle chats; "redacts secrets from generated memory fields"; `memories.disable_on_external_context` excludes chats that used MCP or web search; "Treat memories as a helpful recall layer, not as the only source for rules that must always apply."
- **Cursor Agent SDK** ([memory](https://cursor.com/docs/agent-sdk/reference/memory.md)): a per-turn JSONL journal with no recall tool. "Anyone who can message the agent writes to the journal, so keep the scaffolded rule against following instructions found in records."

## GitHub Copilot Memory: citations verified at read time

- [GitHub blog, 2026-01](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/): they rejected "an offline curation service to deduplicate, resolve conflicts, track branch status, and expire stale information" because of "significant engineering complexity and LLM costs". Instead: "we store memories with citations: references to specific code locations that support each fact. When an agent encounters a stored memory, it verifies the citations in real-time". Example record: `fact`, `citations: ["src/client/sdk/constants.ts:12", …]`, `reason`. At session start "we retrieve the most recent memories for the target repository and include them in the prompt."
- Self-healing: "If the code contradicts the memory, or if the citations are invalid … the agent is encouraged to store a corrected version … If the citations check out … store it again in order to refresh its timestamp."
- Adversarial test: "we deliberately seeded repositories with adversarial memories … Across all test cases, agents consistently verified citations, discovered contradictions, and updated incorrect memories."
- Results (vendor A/B): coding agent PR merge rate "90% with memories vs. 83% without"; code review +3% precision, +4% recall.
- Scope: "Memories for a given repository can only be created in response to actions taken within that repository by contributors with write permissions, and can only be used in tasks on that same repository initiated by users with read permissions."
- [Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory): "an internal voting system … upvote a memory that it's able to validate, and downvote a memory if it's found to be wrong or outdated … Memories that are downvoted past a threshold are no longer used and will be deleted after a period of disuse." Facts "expire after a period without reinforcement". "Because this is a judgment Copilot makes, rather than a guarantee enforced by the system, a stored fact should not be relied on as a rule".
- **For pbrain (inference).** Citations to code locations make a memory checkable against the current code at read time. For pbrain's *observations* and *learnings*, a `source` that points at a file, line or commit lets an agent verify a claim cheaply instead of trusting it. Decisions are different: they are not checkable against code, and Copilot's "use it, then refresh its timestamp" would wrongly let freshness and usage decide them.

## Research on memory for coding agents

- **Experience-following** ([arXiv 2505.16067](https://arxiv.org/abs/2505.16067), 2025-05): "high similarity between a task input and the input in a retrieved memory record often results in highly similar agent outputs", leading to "error propagation, where inaccuracies in past experiences compound" and "misaligned experience replay". Recommendation: regulate "experience quality within the memory bank".
- **CTIM-Rover** ([arXiv 2505.23422](https://arxiv.org/abs/2505.23422), REALM '25): a repository-level episodic memory for a SWE agent "does not outperform AutoCodeRover in any configuration", likely from "noise introduced by distracting CTIM items".
- **Repository memory from commit history** ([arXiv 2510.01003](https://arxiv.org/abs/2510.01003), ICLR 2026): retrieval over past commits, linked issues and summaries of hot files improves code localisation on SWE-bench-verified and SWE-bench-live.
- **REM** ([NeurIPS 2026 listing](https://neurips.cc/virtual/2026/165740); abstract read only through a search summary, **not verified first-hand**): consolidates a trajectory into a document "two orders of magnitude smaller", injects it at task start, gates the fuller record behind a "struggle" detector, and evicts after one exposure. The authors argue "the bottleneck in experience reuse is not retrieval fidelity but lifecycle governance".
- **RD-Forget** ([arXiv 2609.10263](https://arxiv.org/abs/2609.10263), 2026-09): "A superseded fact can mislead a current-state answer and still be essential for a historical query". It "separates what an agent stores from what it uses", using "Same-slot replacement links [to] suppress superseded values in current-state contexts, while intent-aware retrieval makes earlier evidence eligible again."
- Inference: unfiltered episodic memory hurts coding agents. Curated, small, verified items with explicit replacement links help. That is pbrain's model.
