# Google Docs and Meet ingestion

Verified against Google documentation on 2026-11-19. A Google Doc can be downloaded as Markdown in Docs itself or exported through Drive v3. Google Meet stores transcripts and Gemini meeting notes in the organizer's Drive as separate artifacts. A caller with access to the artifact can use the same Markdown import path for either. [Docs UI export](https://support.google.com/docs/answer/12014036?hl=en) · [Drive export formats](https://developers.google.com/workspace/drive/api/guides/ref-export-formats) · [Meet artifacts](https://developers.google.com/workspace/meet/api/guides/artifacts)

## Import ladder

1. **User export.** Open the document, choose File → Download → Markdown (.md), then pass the local file to pbrain with the source URL if it is safe and useful to retain. This uses the user's existing identity and works before a connector exists. Preserve the supplied Markdown bytes separately from any cleanup if original caching is enabled. [Docs export](https://support.google.com/docs/answer/12014036?hl=en#zippy=%2Cexport-a-google-doc-as-markdown)
2. **Drive connector.** With a scoped bearer token, verify `capabilities.canDownload` and use `GET /drive/v3/files/{fileId}/export?mimeType=text%2Fmarkdown` for native Docs. Google documents an exported-content limit of 10 MB. A Drive blob uses `files.get?alt=media` instead. Validate the MIME/type and response before accepting it as Markdown. Capture file id, web link when permitted, modification time and version, plus the hash of returned Markdown bytes. Drive's version includes invisible server-side changes and its SHA-256 metadata is absent for Docs Editors files, so the exported byte digest stays useful. A metadata fetch and export are separate calls. If stronger version binding matters, recheck metadata after export and retry or record the race. [Drive export endpoint](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export) · [Download restrictions and blob downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads) · [Drive file metadata](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)
3. **Meet discovery only when needed.** Given the Docs URL, use the Drive path. When the user starts from a conference record, the Meet API exposes transcript and smart-note metadata, with a Docs destination and a native document id. If normalized per-speaker data is required, `transcripts.entries` gives text, participant reference and timing, but Google deletes those entries after 30 days. The editable Docs transcript can diverge from the API entries and follows Drive retention as configured. The Gemini notes document is generated synthesis, so tag its source accordingly. Meeting settings, organizer access, edition and artifact generation affect what is available. [Meet artifact destinations and retention](https://developers.google.com/workspace/meet/api/guides/artifacts) · [Meet transcript support](https://support.google.com/meet/answer/12849897?hl=en) · [Gemini notes support](https://support.google.com/meet/answer/14754931?hl=en)

Google also documents long-running `files.download` as a distinct download/export method. The basic Docs importer can return a clear oversize or permission error from `files.export`; investigate other export contracts only for a demonstrated need. Markdown fidelity for Docs tables, comments, suggestions, images or speaker-time links needs a live fixture. The bytes returned by Drive are an export representation of an editable Doc. [Download and export options](https://developers.google.com/workspace/drive/api/guides/manage-downloads)

## CLI authorization choices

| Choice | Practical implications |
| --- | --- |
| User downloads, file import | Zero pbrain credential handling. Works when the signed-in user can export. |
| Desktop-app OAuth | Browser consent, Google Cloud project and desktop client, PKCE and a supported redirect such as loopback for desktop. Refresh credentials need secure local storage and must stay out of pbrain records and Git. |
| `drive.file` | Per-file, non-sensitive scope for items opened or explicitly shared with the OAuth app. Have a real file-selection/grant flow. Pasting a URL by itself should not be treated as granting that app access to the file. |
| `drive.readonly`, `drive.meet.readonly` | Export accepts both. The Drive-wide scope covers what the signed-in user can read. The Meet scope covers Drive files created or edited by Meet. Both are restricted, with app verification and, where applicable, security assessments. |
| Existing `gcloud` ADC | Possible for prototyping with a Drive-enabled OAuth client and the required Drive scopes explicitly requested. Default Google Cloud ADC scope and the gcloud CLI's own credentials are distinct. Consumer and corporate Workspace policies can block an OAuth client. |
| Existing Workspace CLI or service account | A separately configured `gws` can act as an external exporter or accept an existing OAuth token. Validate output and avoid depending on its authentication defaults. A service account needs its own file access or organization-approved delegation for user data. The Meet API requires a user principal, which domain-wide delegation can impersonate when authorized. |

Be deliberate about auth defaults because the smallest functional scope can depend on how the document is selected. Google distinguishes app verification from the user's Drive sharing permission, and the Meet metadata discovery scopes are separate from downloading from Drive. [Google desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) · [Drive scope guidance](https://developers.google.com/workspace/drive/api/guides/api-specific-auth) · [Drive export scopes](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export#authorization-scopes) · [Meet scopes and delegation](https://developers.google.com/workspace/meet/api/guides/authenticate-authorize) · [ADC setup](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment) · [Workspace CLI v0.22.5](https://github.com/googleworkspace/cli/blob/v0.22.5/README.md#authentication)

Fetching a private document and republishing the body to a repository are distinct permissions. Import should use explicit sharing scope and keep protected artifacts and provenance out of shared Git unless the operator is authorized to republish to those readers. Google API Terms §5(e) addresses permanent copies and derivative uses, with exceptions for permission from the content owner or applicable law. Its user-data policy calls for disclosure, limited use and secure handling. Test the product flow with the actual Workspace plan, admin policy and content-owner permissions before supporting an authenticated connector. [Google API Terms](https://developers.google.com/terms#e-prohibitions-on-content) · [Google API Services User Data Policy](https://developers.google.com/terms/api-services-user-data-policy) · [Workspace admin app controls](https://knowledge.workspace.google.com/admin/apps/control-which-apps-access-google-workspace-data)
