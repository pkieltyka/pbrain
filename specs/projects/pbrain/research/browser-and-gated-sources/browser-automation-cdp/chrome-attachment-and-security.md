# Attaching to a signed-in Chrome session

Reviewed 2026-11-19 against Chrome's public documentation and tagged tool sources. The Chrome attachment flows below are documented capabilities. No browser, signed-in session, or local browser configuration was used for this research.

## Choose the connection by its exposure

| Route | What Chrome exposes | Fit for pbrain capture |
| --- | --- | --- |
| Site export using the person's normal browser | The person saves the selected document through site controls. | First choice when the site offers the right file. Works when browser automation is unavailable or the material cannot be shared with an agent. |
| Chrome 144+ with the browser's remote-debugging consent UI | The person enables debugging in the running browser and approves the connection. The agent inherits the selected profile's open windows and signed-in state. | Most portable automated Chrome route when the user trusts the client with the entire profile and approves this capture. |
| Separate, dedicated Chrome user-data directory | A separate cookie jar, profile, tabs and storage. The person can sign in to an authorized site when the provider allows it. Client can launch this instance or attach to an explicitly configured loopback endpoint. | Prefer for recurring work or a primary profile with unrelated sensitive tabs. Requires setup and sign-in. |
| Chrome for Testing or ephemeral browser context | A clean automation environment with no inherited sign-in. Chrome for Testing retains support for the legacy debugging switches. | Suitable for public JavaScript pages and test fixtures. |

[Chrome's auto-connect guide](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect) · [Chrome 136 switch restriction and Chrome for Testing exception](https://developer.chrome.com/blog/remote-debugging-port) · [DevTools MCP advanced usage, v1.13.0](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/chrome-devtools-mcp-v1.13.0/docs/advanced-usage.md)

## Two different debugging mechanisms

- **Command-line ports and pipes.** Since Chrome 136, regular Chrome ignores `--remote-debugging-port` and `--remote-debugging-pipe` with its default user-data directory. Chrome requires a non-default `--user-data-dir`, with a different encryption key. A named profile under the same default directory does not satisfy the requirement. Choose a fresh dedicated directory for automation. Do not copy a person's profile database or export its credentials. [Chrome security announcement, March 2025](https://developer.chrome.com/blog/remote-debugging-port)
- **Browser consent in Chrome 144 and later.** The person opens `chrome://inspect/#remote-debugging`, enables the feature and approves Chrome's prompt when the local client connects. No restart with legacy flags is required. With multiple active profiles, DevTools MCP documents that Chrome determines the default and the client sees all open windows of that profile. Verify the actual target and account with the person. The Chrome guide explicitly lists cookies, local storage, session storage and open tabs in the scope of attachment. [December 2025 introduction](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session) · [Current auto-connect guide](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect) · [Tagged advanced usage](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/chrome-devtools-mcp-v1.13.0/docs/advanced-usage.md)
- **Discovery differs.** The traditional port supports HTTP discovery and a browser WebSocket. The Chrome consent flow can provide a dynamic port and a WebSocket through supported local tool discovery while returning 404 from `/json/version` or `/json/list`. Use the tool's named connection mode for this flow. Avoid asking the person to find and paste a browser WebSocket URL, or publishing it in logs or configuration. [CDP protocol and HTTP endpoints](https://chromedevtools.github.io/devtools-protocol/) · [DevTools MCP issue #2283 and maintainer explanation](https://github.com/ChromeDevTools/chrome-devtools-mcp/issues/2283) · [Agent Browser's tagged discovery notes](https://github.com/vercel-labs/agent-browser/blob/v0.43.0/docs/content/docs/cdp-mode.mdx)

## Playwright for a local scripted handoff

`chromium.connectOverCDP(endpointURL, options)` accepts an HTTP discovery URL or a browser WebSocket URL and exposes the existing default browser context. The current 1.65.1 release (November 13, 2026) also accepts a supported browser channel such as `chrome`. Tagged source confirms that channel mode resolves the local `DevToolsActivePort` file to a WebSocket and skips HTTP discovery. Pair that mode with the person's Chrome consent flow on a supported local configuration. Older installations need a version check and may only take URLs. Playwright describes CDP attachment as lower fidelity than its own connection protocol and restricts CDP attachment to Chromium. [BrowserType API](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp) · [v1.65.1 release](https://github.com/microsoft/playwright/releases/tag/v1.65.1) · [v1.65.1 Chromium attachment source](https://github.com/microsoft/playwright/blob/v1.65.1/packages/playwright-core/src/server/chromium/chromium.ts)

Use `noDefaults: true` (added in 1.60) when attaching to a person's context so the connection leaves download settings, emulated focus and media defaults alone. Identify the intended page and frame explicitly. A script can write locally without pasting the entire page into the model conversation, if its inputs and outputs are kept local by design. Browser-managed downloads or user-provided files are the reliable fallback when attachment does not yield a compatible download event. Playwright documents the normal event-and-save path for its supported contexts. [BrowserType API](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp) · [Frame locators](https://playwright.dev/docs/frames) · [Downloads](https://playwright.dev/docs/downloads)

## Consent and data handling

- **Scope the operation to the named document.** Ask the person to open the target and approve the intended use and destination. Work by page ID or explicit tab handle. Confirm the URL or title again before saving, especially after redirects or tab changes. A tab handle prevents targeting mistakes. Browser-level CDP still grants wider capability. Extensions differ in tab adoption and origin controls. [Chrome's list of profile-wide access](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect) · [Browse security model](https://github.com/anomalyco/browse/blob/v0.1.5/README.md#security)
- **Keep the connection local and narrow in time.** Use the Chrome prompt or an owner-approved, dedicated loopback port. Keep remote forwarding, public listeners and ad hoc browser relays out of this workflow. Keep credentials in the browser. The person performs any sign-in or MFA. Avoid cookie and storage inspection, auth-state export, network recordings, and unrelated tabs. Disconnect after the file is saved and have the person turn off temporary debugging. [Chrome auto-connect setup and privacy](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect) · [Playwright authentication state warning](https://playwright.dev/docs/auth#core-concepts)
- **Treat page content and tool output as untrusted data.** The page may contain instructions aimed at the agent in visible or hidden content. Constrain actions to the user-directed read/export. Keep permissions, sharing settings, uploads, edits, page-supplied code, arbitrary tool invocations and outbound transfers outside that operation. Favor a bounded local save and check what the harness logs or sends to the model. A local browser process alone does not confine the returned content. [OWASP indirect prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html#remoteindirect-prompt-injection) · [Chrome DevTools data disclosure](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect)
- **Treat retaining content as a separate permission.** A user can see a document that they cannot copy or share with the repo. Stop if site policy forbids copying or downloading, or if the person cannot approve retention. Use a safe source URL with no passwords, session tokens, or secret-bearing query parameters. A local original keeps its sensitive bytes, and a shared Markdown body reaches readers once committed. Section 12 bars sending personal material off-machine. Verify local-only handling before an agent or remote harness reads it, or let the person save and import it locally. [Claude artifact permissions](https://support.claude.com/en/articles/9547008-share-artifacts) · [pbrain spec §§8.4 and 12](../../../functional_spec.md)

## Deployment caveats

DevTools MCP's tagged troubleshooting guide documents macOS privacy errors when the terminal or IDE cannot read Chrome's discovery file. It also describes Chrome versions through 149 with frozen tabs that can slow a connection. Browser channel, OS permissions, and enterprise policy can prevent attachment. Treat this as a clean fallback to the person's export or an authorized dedicated profile. This pass did not test managed devices, profile selection, sandboxed clients, or a live consent prompt. [v1.13.0 troubleshooting](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/chrome-devtools-mcp-v1.13.0/docs/troubleshooting.md)
