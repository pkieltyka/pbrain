# Architecture review, round 1 — architect-2

Reviewed architecture `c5c5342b` against the complete functional spec `4622a82f`. I recommend the scan-first design and a second phase for component detail. The section-scanning rules, file-read boundary and write commit point need decisions in this document because several packages depend on them.

## Blocking

1. **The scanner drops the personal section (§§6.2–7.1, spec §§2.2, 5.1–5.3).** The guard requires the personal directory to be Git-ignored, then the common scanner discards its ignored files. In a temporary Git tree with the specified ignore rules, Git reported an ordinary personal Markdown item as ignored. Consequently `get --personal`, search, tag counts and incoming links all lose it. Apply Git ignore filtering only during shared-item discovery. Walk a reachable selected personal root with its dot-folder, regular-file and no-link rules. For shared discovery prune guarded or ignored directories before enumerating their contents. **Prove** the same personal item is retrievable with the flag and absent from shared results, totals and errors.

2. **There is no file-input boundary shared by `add --body-file` and file import (§§2–3, 6.3, 10.2, 11.1–12, spec §5.2).** The exposure guard establishes that private storage is safe on disk. It does not determine whether a caller may copy a particular file into a shared item. No interface applies that decision to both callers before bytes or an original are acquired. Put destination selection before item lookup, input or acquisition. Give both commands one guarded file opener which resolves the input, applies all protected-path and case-insensitive `.pbrain` ancestor rules, and exposes the same failure as a missing file. Apply section confinement and no-link traversal to store-owned paths at the actual open, create or removal too, including parents of `originals/`. **Prove** scenario 6 through both commands, with no cache or partial item on refusal.

3. **A header-only scan cannot decide item eligibility, and `BodyAt` can refer to yesterday's header (§§4.1–4.3, 5, 7.1, 8.3–8.4, spec §§2.4, 8.1, 9.3).** A readable header followed by invalid UTF-8 currently contributes to `list`, title hits and graph currentness. The spec skips that entire file on every read. Also, a normal concurrent `verify` can atomically lengthen the header between scan and `Catalog.Body`. Applying the old byte offset to the new file mixes two versions in one result. Validate the entire bounded file before publishing its header into the catalog. Tie any deferred body to the same observed file version, or reload and retry the affected command on change. Avoid retaining an open descriptor per corpus item. **Prove** a malformed-body item cannot replace another, and a concurrent verification yields a coherent header, snippet and body.

4. **Canonicalization and fetch checks must apply at the point where the audience or connection is chosen (§§11.2, 12, spec §§8.4–8.5).** The path procedure rejects dot segments before decoding unreserved characters, although the decoded segment can itself be a dot segment. The fallback also omits the spec's requirement for an explicit audience when a source has no canonical form. Specify one escaped-path pipeline for rules and sources, validate the decoded segments, then match or require the explicit flag. For fetching, the spec validates the host at *each request and redirect*. A transport dial callback runs per new connection and may be skipped on reuse. Validate each hop before the request and bind that request to a checked address, retaining TLS hostname verification. **Prove** canonicalization parity and per-hop checks using the controlled fixture, including same-host redirects. [Go HTTP transport](https://pkg.go.dev/net/http#Transport)

5. **Write outcomes become ambiguous after publication (§§10.1–10.4, 12–13, spec §§8.1, 8.5–8.6).** A new file already exists once the final hard link succeeds. A later failed temp cleanup or directory flush cannot truthfully return the usual “nothing written, retry” error. Likewise, a successful delete can be followed by a failed flush. State the visibility commit point and the post-commit notice/outcome for each operation. Hold the target-section lock through digest-reference checks and original cleanup. Resolve an existing item's section before locking and revalidate under that lock. A preview on a fresh clone must not create `.pbrain/lock` or any folder. For `audience set/unset`, reload the latest `personal.toml` **under** its lock before applying the single edit, otherwise two commands can each rewrite the stale config loaded in `Open`. **Prove** first-write preview, concurrent rule setters, import racing cleanup, and injected failures on each side of publication.

6. **Git guard and init need usable behavior on an empty checkout (§§1–2, 6.2–6.4, spec §§5.3, 9.2).** In a scratch Git repo I confirmed that an absent `personal` or `.pbrain` sent to `check-ignore` without the trailing slash misses the directory-only rule. The directory-form probe matches. Exit 1 from this Git query means no match, not a Git failure. Preserve file vs. directory information when probing absent protected paths, use literal path arguments, handle Git's exit statuses explicitly, and keep guard checks separate from scan filtering. `init` must add missing rules to an existing ignore file while preserving its contents. Dispatch `init`, `skill`, help and version before the generic Open/Scan pipeline. Keep the proposed repo-wide second-brain search behind an owner-approved amendment. A fixture containing a file called `pbrain.toml` outside the chosen brain would otherwise block a valid init. **Prove** a clean init with absent protected folders, idempotence with a partially populated ignore file, and a brain-free skill lookup. [Git check-ignore](https://git-scm.com/docs/git-check-ignore)

## Should fix

1. **Required zeros and the smallest usable budget (§9, spec §§6.1–6.2, 7.1–7.5).** Omitting every zero loses `snippet_offset: 0`, a zero `alone` count and a declared tag's zero `items`. All convey information. Specify presence field by field. Count code points in the *encoded* JSON, including escapes and newline. For `get`, reserve the linked locator and footer and one body character when required before granting space to extras. Test a long linked locator, an escaped multibyte body and the stated minimum in both modes. The optional `more: 0` amendment is a separate decision. [Go JSON encoding](https://pkg.go.dev/encoding/json#Marshal)

2. **Standing must normalize exceptional kinds (§§4.1, 7.2, 8.3, spec §§3–4).** The three-level helper comment gives rank 2 to any verified item without a decider, which includes a decision missing its decider and a source hand-edited to claim verification. Both have provisional standing. Preserve recorded fields for diagnostics and status filters, derive effective standing once with explicit cases for these kinds, and use it in ranking, replacement validation, rendering and prime. Test both cases.

3. **A header match still needs a body passage (§§8.2–8.4, spec §7.1).** Step 2 skips the body for a title match. Section 8.4 limits the passage pass to bodies already known to match. This loses the most useful passage even when the source title matches perfectly. For every returned item with a nonempty body, choose the earliest highest-coverage 200-code-point window from the body, including the prescribed start-of-body fallback; preserve the winning clauses when flattening or cutting the displayed excerpt. A title-only hit and a long article with a perfect title and a later matching passage distinguish these cases.

4. **Use a package graph that builds (§§2–4, 8.5, 18).** `brain.LocalConfig` imports `audience.Rule`, opposite the declared dependency order. `graph.Build` takes a store catalog and `store.Scan` takes a brain, so steps 1–4 are not independently buildable from `item`. `Catalog.Items` is a field and cannot also implement `Corpus.Items()` under that name. Give the catalog an accessor with separate backing storage or pass the concrete catalog. Put the dependency-free rule parser/type below `brain`, then order store and graph above it. Prefer one concrete lexical entry point until a second strategy is approved. Show how `errs.Error` implements Go's `error`. A small compile check of the shared signatures should precede parallel implementation.

5. **Measure the reference implementation under the promised workload (§§7.1, 8.6, 14, 16 Q7).** The warm two-word microbenchmark supports trying a scan. It excludes whole-file validation, YAML node parsing, Git, the guard, graph construction, output and process start. It cannot establish the 300 ms read target. Retain scan-first and measure the built CLI on both supported operating systems against cold and warm fixtures, separating the 10 s first-read target from subsequent calls. Publish the timings and the threshold for revisiting an index. Include a plain checkout and one with personal data.

6. **Keep semantic constraints independent of the candidate algorithm (§§8.5–8.7, 17, spec §§1, 7.1, 16–17).** An optimization of lexical search must preserve lexical results. Requiring *any* later engine to return the identical ids and order rules out finding the very paraphrases under research. Restrict byte/ordering equivalence to implementations of the same approved mode. Carry shared visibility, standing, lifecycle, budgets, citations, determinism for fixed inputs and rebuildability into any later mode. Research informs an owner-approved amendment before behavior, networking or model use changes. No semantic engine choice is required in this review.

**S3 proving case.** In a long body whose sole matching word `queue` occupies code points [1000, 1005), a 200-code-point excerpt can first contain the whole match at offset **805**. If the intervening characters are punctuation and the next word starts at 1000, §8.4 returns **1000**. I compared the two candidate sets in a scratch check. Allow every code-point start and choose the smallest among windows with maximum whole-clause coverage. For a winning span ending at 1005, that gives `max(0, 1005 - 200) = 805`. Add this case to §14 so the renderer and `get --offset` agree. If word alignment is preferred, it changes the approved passage rule and needs the owner's decision.

**Verdict — changes required.** No blocking findings remain. Only S3 requires a correction or an owner decision.
