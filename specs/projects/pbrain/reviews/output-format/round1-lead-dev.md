# Output format — round 1

Keep v1's plain default and compact JSON. Search should help an agent choose what to open. The existing offset and outline give it a precise next read. Use the long-source fixture to decide whether another locator or preview would help. I propose no v1 output amendment. [Owner question](owner-question.md) · [Sections 6 and 7](../../functional_spec.md)

1. **Agent default.** Plain structural lines for results and metadata, and the stored Markdown body in `get`. Markdown headings, fences and links in a body carry information worth preserving. Wrapping every search row in extra Markdown headings or tables would spend budget on layout and can require escaping source text. Preserve the single-line snippet in v1. The agent can read a fitting body, jump to a long hit with `get --offset`, or use `get --outline` to choose a section.
2. **Line numbers and `get --line`.** Later, if pilots show agents or people repeatedly need line-based navigation. Offer one 1-based body-relative start line on demand before considering ranges or a second get locator. Keep the code-point offset as the exact position. A snippet can start halfway through a line, and the stored body may differ from the original document's lines. Define any added line locator against the stored body, before wrapping or flattening. A 12-character label on each hit costs 60 characters at five hits. It can displace related evidence or the final row on a tight page.
3. **Occurrence counts.** Skip a general per-item count. `partial 2/3` already explains clause coverage. A count of repeated words on a long page cannot establish relevance, phrases and prefixes need explicit semantics, and a semantic hit may contain none of the query's words. Full frequency counting can also remove strict search's early stop. A later opt-in lexical diagnostic could count body occurrences per clause if a task demonstrably needs it. It should be excluded from ranking and follow the same view restrictions. The v1 empty-page clause counts remain the compact retry aid.
4. **Context lines.** Keep the 200-code-point evidence stretch and use a second `get` in v1. Adding one 80-character line on each side costs about 162 code points per row. For example, five 350-character rows and a 50-character footer fit today, while those context lines would leave room for only three full rows at the same budget. Measure first-page correct IDs and whether the supporting passage became visible after the read, including the read's cost. If the pilot needs neighboring lines, start with an explicit bounded `get` window around the selected offset. Keep a search preview opt-in and optional after main rows if it still earns a place. Count actual printed line breaks and indentation, including escapes in JSON.
5. **Terminal presentation.** Plain v1 is readable and redirectable. A later explicit `--pretty` could color structural labels and wrap the display. Keep color and width out of default output, even on a TTY, so an agent gets the same bytes via a terminal and a pipe. The option should share the same view, ordering, abstention and visible budget. It should be mutually exclusive with JSON and add only renderer-controlled decoration.
6. **JSON and a future API.** Compact JSON is enough for v1 automation. Treat the documented types, fields, omissions, notices, errors and offset units as a tested contract now. Golden fixtures should cover empty results, a tight page and a semantic notice alongside stdout. Add a formal schema if consumers need validation and choose a versioned envelope when an API exists or a breaking contract change needs one. An extra envelope field costs little once per page, but it buys no compatibility on its own and changes current fit. A future HTTP service also needs its own request, authorization and pagination contract.

All presentation options operate after match admission and filtering. Retaining an empty page when the search finds no acceptable evidence is part of the contract in either format. [Evidence measurement](../../components/semantic.md#calibration)
