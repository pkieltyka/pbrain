# Output format — independent view

**For v1, keep plain text for reading and compact JSON for programs.** A search page helps an agent choose its next read. A short claim can answer the question on that page; a long source needs a dependable jump to the passage. I would spend the default 2,000 characters on those two jobs.

1. **Agent format — v1.** Keep the short text header, citation and one flattened snippet. Preserve the original Markdown in `get` so code fences, lists and heading levels survive. For a long hit, use its ID and zero-based Unicode code-point offset with `get`, or read its outline; use the returned continuation for more of a body. A Markdown table around search hits would spend characters on delimiters and escaping. This choice costs no new output and leaves empty results alone.
2. **Lines, counts and context.** Keep offsets in v1. They address the exact start of a passage even in a single long Markdown paragraph. A title-only match or a semantic hit may have no matching body line. If editor navigation proves common, add an opt-in, one-based *body* line and `get --line` together later; keep the offset for precise continuation. Five labels such as ` [line 123]` cost 55 characters before JSON overhead. Skip per-item occurrence counts in v1. Three repetitions of “retry” do not make a provisional note authoritative; counting all occurrences also defeats early exit in strict search. The existing `partial 2/3` already conveys clause coverage; semantic evidence need not contain a literal occurrence. Keep the empty-result hints scoped as today. **Defer `--context N`.** With two 80-character lines on either side of each of five snippets, context alone adds about 1,600 characters plus line breaks. The 200-character snippets alone can take another 1,000. Whole hits then disappear behind continuation. For surrounding text today, open the chosen item slightly before the returned offset. Use the evidence fixture to see whether this extra call earns a context option. Any future display option acts only on admitted hits and preserves an empty page.
3. **Human terminal — later, explicit.** Text is already readable and the terminal can soft-wrap it. Keep stdout identical in a pane, a pipe and a file in v1; agents also run in TTYs. If human use warrants a pretty mode, offer an explicit text-only option for highlighting pbrain’s own labels. Keep it off for JSON, preserve copyable IDs and offsets, and measure any emitted escape sequences under the same budget. Colour changes neither admission nor standing. Reflowing stored code and rendering arbitrary Markdown are poor defaults.
4. **API — stabilize the JSON contract in v1; version the network API when it exists.** Document fields, types, omission versus zero, units, paging, notices on stderr and exit codes. Pin these with small success, empty and failure fixtures and require clients to tolerate unknown optional fields. This adds zero characters to output. A mandatory version member on every read buys little before an incompatible revision; an HTTP wrapper can later version the transport and map stdout/stderr explicitly. Test budgets and empty pages on each rendered form independently. Quoting and escaping can make fewer hits fit in JSON.

**Owner proposal:** keep the current default and prioritize JSON compatibility fixtures and evidence-reach measurements. Revisit line navigation, context and terminal styling when observed use identifies which one saves a read. [Functional spec §§6–7](../../functional_spec.md)
