## Blocking

1. **A shared write can consume a personal item by path (§§2.2, 5.2, 8.2, 8.4).** Default `get` hides a personal transcript, but `import <personal transcript.md>` accepts a local Markdown file and defaults to sharing its copy and caching its original. `add --body-file` has the same issue. This does not require the user to paste protected text into a new file. Enforce the input boundary before opening an explicit path, including aliases, when its resolved location is in known personal storage or its cache. Fail a shared write without identifying the protected item. Keep stdin under the documented caller-responsibility rule. For `import --personal`, look up bare-link promotion candidates only in the destination section, even when a shared link has the same URL. Test both explicit file inputs and a URL present only as a shared link. The shared item and shared cache must stay untouched.

2. **External personal storage can put original bytes back within reach of Git (§§5.1–5.3, 8.4, 18.3).** An external repository is expressly allowed. Its own `.pbrain/` receives original transcripts, while the ignore file written in the project has no effect there. Nothing checks whether that cache is already tracked or eligible for the next ordinary `git add`. This conflicts with owner answer 9 and the promise in §8.4, even if the owner deliberately versions normalized personal notes separately. Keep external Markdown under the owner’s control. Place originals in local storage protected from both repositories, or verify that the repository containing the cache ignores it and has no tracked entries. A personal import into an external repo with an unprotected cache must fail safely or use the protected location. Clarify that the project guard still protects the default local personal directory and marker when an external root is configured.

3. **A committed item can outlive its only copy of the original (§§8.1, 8.4, 9.3, 15.15).** §8.1 brings local data up to date after publishing the item and promises the next command repairs failures. §8.4 requires the exact original and explains why it cannot be rebuilt. If the original write fails or the process stops after the item appears, index repair cannot produce those bytes. Make successful persistence of a digest-checked original a precondition for publishing an acquired item. Then publish the one Markdown file and permit the index update to fail independently. A rejected write may leave an unused raw blob in its proper section. Exercise failure at the raw-cache write, between cache and item publication, and after publication. No published acquisition should point to a never-saved original. Later user deletion remains valid.

## Should-fix

4. **Read and write eligibility disagree (§§2.1–2.2, 8.1–8.2, 15.9).** “Tracked files plus untracked files that are not ignored” includes a tracked file under an ignore-matched legacy directory. “An ignored folder of any name is never read as shared” excludes it. I checked on an existing tracked file with a temporary exclusion: ordinary Git ignore lookup skipped it, while lookup independent of the index matched it. Specify that an ignore-matched directory is pruned before shared traversal, including any tracked descendant. Conversely, if Git ignores the default shared `notes/` destination, an `add` may succeed with an item no subsequent read can find. Validate the final path against the same shared eligibility rules before publishing. Test both cases.

5. **The documented adoption paths do not preserve the corpus (§§5.1, 5.4, 13).** §13 proposes pointing `personal.yml` at factory’s existing private folder. §5.1 requires an override outside the worktree. With that restriction, document moving an in-project folder to the reserved personal location or outside the project. Also fix the qmd guidance: excluding only `personal/` and `.pbrain/` still admits the old ignored folder of another name. Require an explicitly shared-only collection whenever qmd is used. The project’s recorded qmd fixture found that Git ignore rules alone do not filter its corpus.

6. **Legacy edges and advancing forks lack one lifecycle rule (§§4.2–4.4, 7.2, 9.1, 15.11–12).** A legacy stamp can name itself or complete a cycle with a modern edge. §4.4 would hide a note whose target resolves uniquely, while §4.2 discards cycle edges. Normalize a resolved legacy stamp into the same graph before cycle detection, with its stated standing exception. Spell out precedence if a modern successor and a conflicting legacy stamp coexist, favoring the authoritative modern evidence. For forks, suppose B and C replace A and later D replaces only B. A still has two live outcomes, C and D, but the “two current items replace the same item” test stops warning. Diagnose unresolved distinct current successors until a join leaves one. Test mixed cycles, an advancing fork and the subsequent join.

7. **An empty page can exceed a hard cap (§§6.1–6.3, 7.4, 11, 15.17).** With an empty brain and `--max-chars 1`, the two required prime header lines, or even an empty JSON object plus newline, do not fit. There is no first item to trigger the minimum-limit error. Define the minimum for the mandatory empty envelope/footer and for an empty body or offset at end. Return `budget_too_small` if that minimum does not fit. Define zero, negative and past-end offsets and preserve the query, filters and view when giving a continuation. Check page traversal against fixed files **and time**, as §11 already does for determinism.

8. **Ranking has two contradictory comparisons (§§2.4, 7.1, 11, 15.1).** The ordered keys put standing ahead of exact time within one recency band. The next sentence says a newer equally matching item always wins regardless of standing. Keep the operator-confirmed key order, correct the sentence, and put both dates in a named band in scenario 1. Define the exact UTC boundaries (including future times) and put unrecoverable missing/invalid `created` values in a defined last position with a visible unknown date. For a quoted phrase, a title containing its words out of order should not earn the title-match class merely because the actual phrase occurs in the body. Classify the field match with the same predicate that admits the item. Test same-band and cross-band ties, the exact boundary, and the phrase case.

9. **The write and read promises extend beyond cooperating writers (§§8.1, 9.3, 11).** A hand editor can save a change between pbrain’s comparison and publication. A multi-file scan concurrent with a Git checkout need not correspond to the instant the command started. Scope the guarantees to pbrain’s cooperating writers, lock by actual destination section (including two checkouts pointing at one external section), and define normal reads against one completed scan or index generation. For direct hand edits, return `conflict` for a detected change before publish and document the residual race. After interruption before acknowledgment the caller may have to inspect the store. Reserve “safe to repeat” for a known pre-publication failure.

10. **URL promotion and replacement need a unique target (§§4.2, 8.1, 8.4).** Two branches can each create a bare link for one URL under different ids and merge cleanly. A plain import can now select either for in-place mutation. It is also unclear whether an unrelated `--replaces X` bypasses the duplicate-current-URL rule, or whether flags such as `--tag` silently disappear when a link is promoted. In the destination section, promote only one unambiguous current bare link with that locator; reject ambiguity without changing an item. For an explicit replacement, create a new source file, validate the specified predecessor(s) and exempt from duplicate checks only the source(s) being replaced. Define which flags are accepted during promotion and refuse a hand-edited nonempty link body before overwriting it. Test the two-branch merge and replacement of a different id while the URL already exists.

11. **The URL release gate disagrees with the fetch contract (§§8.4, 15.20, 16).** §8.4 ignores environment proxies and validates every actual connection. Scenario 20 instead requires failure merely because a proxy is set or DNS contains both public and private addresses. Under the drafted policy a direct public connection can succeed in either case. Require the fixture to prove the proxy received no request and every connected peer was permitted; a mandatory proxy can leave the direct route unavailable. Explicitly define the original/hash bytes relative to HTTP content decoding: the stored original and its hash must use the same representation. Distinguish that boundary from the two independent input size limits. This clears the URL phase’s release gate without requiring more provenance fields.

12. **The writable YAML subset contradicts its CRLF test (§§2.4, 8.3, 15.16).** An affected field must be “in the form pbrain writes,” which §2.4 defines as LF. Scenario 16 requires a CRLF file to be patched while preserving other bytes. Allow either newline style for a supported single-line field, preserve the existing style when inserting a field, and refuse an unsupported affected representation before changing the file. A comment or unknown key elsewhere should survive unchanged.

## Reviewer choices and declined changes

1. **Recency bands.** Keep 30, 180 and 365 days for v1. They implement a meaningful distinction between recent and historical evidence without changing which items are current. The within-band rule and boundary fixtures in finding 8 are sufficient to evaluate them.
2. **Proxy settings.** Keep direct connections and the documented file-import fallback for a mandatory proxy. Reconcile the acceptance test with that choice (11).
3. **External personal repository and exposure reporting.** Accept the decline of blanket Git checks on an independently managed collection of Markdown. The originals cache still has the owner’s untracked-storage requirement (2). Accept one generic exposure error, including for `check`. A path category and remediation suffice for a shared-mode command; item names would disclose protected information.
4. **HTML floor and budgets.** Keep the 200-code-point HTML heuristic and proposed read defaults as starting values. Include a legitimate short static page in the fixture to make the deliberate rejection and bare-link fallback explicit. Keep the cap absolute for empty outputs as well (7).

I agree with deferring persistent **final URL and converter version**. Resolving relative links against the final URL during this acquisition is sufficient for v1. I also agree with deferring **source-permission inference**. An explicit import, visible destination and `--link-only` give the person making the choice control over retention. Neither decline waives the storage and publication guarantees for originals the CLI does acquire.

**Verdict — changes required.** Three blocking and nine should-fix findings.
